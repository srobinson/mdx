## Executive Summary

`runtime-matters` has a build script in `crates/rtm-cli/build.rs` that writes committed documentation and Rust source files back into the repo during Cargo builds. Pane A's redrafted discovery document accurately captured the main rabbit hole: README generation is only one symptom of a wider build time source tree write pattern.

My audit signed off conditionally. The draft needs four corrections before it is ready as the shared discovery artifact: one item creates a broken build ordering, one leaves dead `tools.toml` registry fields behind, one test classification is too broad, and one preface overstates which surfaces are generated by `rtm-cli/build.rs`.

## Project Metadata

- Language: Rust workspace.
- Build system: Cargo plus `just` recipes.
- Rust version: workspace declares `rust-version = "1.90"` in `Cargo.toml:21`.
- Main crates in scope: `rtm-cli`, `rtm-core`, `rtm-daemon`.
- Key dependencies in this rabbit hole: `toml`, `serde_json`, `clap`, `insta`.
- Verification state: local `fmm validate` passed with 135 indexed files current. The fmm MCP endpoint had a schema mismatch earlier, so local `fmm` CLI was used for structural verification.

## Architecture

The central source is `crates/rtm-core/tools.toml`, also exposed through the repo root `tools.toml` symlink. `crates/rtm-core/src/tool_contracts.rs:66-70` parses it into `ToolRegistry` through `include_str!` and `toml::from_str`.

`crates/rtm-cli/build.rs` writes tracked files during build:

- Root `README.md`, through `write_readme()` at `crates/rtm-cli/build.rs:97-106`.
- `crates/rtm-cli/src/generated/mod.rs`, `cli_help.rs`, `contracts.rs`, and `mcp_tools.rs`, through `write_generated_sources()` at `crates/rtm-cli/build.rs:79-89`.
- `crates/rtm-cli/templates/SKILL.md`, through `write_skill_doc()` at `crates/rtm-cli/build.rs:91-95`.

The daemon runtime does not consume the generated MCP constants. It serves live MCP `tools/list` output from `contract_registry().tool_list_value()` in `crates/rtm-daemon/src/mcp_bridge.rs:33-37`.

## Key Patterns

- Build script source tree writes are the core smell. Cargo build scripts conventionally write to `OUT_DIR`, but this script writes committed docs and Rust modules.
- The generated MCP tool list duplicates the runtime registry. Tests compare runtime output to a generated constant that is produced from the same `tools.toml` source.
- Snapshot tests currently pin generated artifacts rather than only runtime behavior.
- `PROJECT.md` contains `rtm-admin-tools` markers but is not written by the generator. It is a drift surface, not a generated surface.

## Detailed Findings

### 1. Item 3 has a broken build ordering

Pane A's Item 3 says `rust_string()` can be deleted when only `generated/cli_help.rs` is removed. That is unsafe because `build.rs::mcp_tools()` still calls `rust_string()` at `crates/rtm-cli/build.rs:135` while Item 5 is optional. The deletion must move to Item 5 or Item 6, or Item 3 must depend on Item 5.

Verification:

- `crates/rtm-cli/build.rs:115` uses `rust_string()` for CLI help generation.
- `crates/rtm-cli/build.rs:135` uses `rust_string()` for MCP tool name generation.
- `crates/rtm-cli/build.rs:211-213` defines `rust_string()`.

### 2. Item 2 leaves dead registry fields behind

Item 2 deletes `generated/contracts.rs` and `contract_aliases()`, but it does not address `args_type` and `response_type`. After removing the contract alias generator, these fields remain as dead schema data unless another consumer is identified.

Relevant paths:

- `crates/rtm-core/src/tool_contracts.rs:20-21` defines `args_type` and `response_type` on `ToolContract`.
- `crates/rtm-core/tools.toml:9-10`, `59-60`, `115-116`, and `144-145` define those fields for each tool.
- `crates/rtm-cli/build.rs:157`, `162`, `168`, and `174` are current consumers through the alias generator.

Recommended correction: add those paths to Item 2 or split them into a dedicated optional cleanup item.

### 3. Test classification should be narrower

The draft says `admin_tools_readme_section_is_stable` survives if the registry stays. That is too broad. The test snapshots `contract_registry().admin_tools_markdown()`, so it only survives if a markdown surface such as `SKILL.md` remains generated. For the user's README intent, it should be treated as support for generated README content unless deliberately renamed and scoped to a surviving non README surface.

Relevant path: `crates/rtm-core/tests/tool_contract_snapshots.rs:8-11`.

### 4. Surface preface overstates `rtm-cli/build.rs` ownership

The draft preface says every surface below is produced by `crates/rtm-cli/build.rs::main()`. That is true for Surfaces A through F, but not for the adjacent metadata surfaces and drift surface:

- Surface H is produced by `crates/rtm-core/build.rs:3-14`.
- Surface I, `PROJECT.md`, is explicitly not generated.

Recommended correction: scope the preface to Surfaces A through F, then introduce G and H as adjacent build metadata and I as drift.

## Dependencies

- `toml`: parses `tools.toml` into `ToolRegistry`.
- `serde_json`: builds MCP `tools/list` JSON payloads and generated JSON constants.
- `clap`: consumes some generated CLI help constants.
- `insta`: snapshots generated artifacts and runtime surfaces.
- cargo-dist: packages root `README.md` for binary releases via `Cargo.toml:90`.

## Relevance to Helioy

This is a good example of why source tree generation from build scripts should be treated as a boundary smell in Helioy repos. The immediate README autonomy fix is small, but the deeper cleanup should remove test only generated artifacts and keep runtime contracts owned by one explicit source.

## Open Questions

1. Should the batch stop at README autonomy, or should it remove all `rtm-cli/build.rs` source tree writes?
2. Should `PROJECT.md` keep a manual admin tools table, or should its copied marker section be removed?
3. Should `tools.toml` remain the runtime MCP source of truth, or should the registry move to direct Rust definitions?
4. If `SKILL.md` has a future shipping path, should it become hand owned rather than generated?

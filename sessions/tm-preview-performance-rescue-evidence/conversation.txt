## Think before you touch

Before any change (a text tweak, a one-line edit, or new code), apply the judgment a senior engineer applies before touching code. A request to make a change is not permission to skip it. The only exception is an explicit "do exactly this, do not think".

- Consistency: does it match the surrounding conventions (casing, naming, structure, patterns)?
- DRY: does an equivalent already exist? Search first, then reuse or refactor so callers share one path.
- Placement: where is the best home for new code, for cohesion and navigability?
- Blast radius: what ripples from this? Even a one-line change can reach callers, generated surfaces, and contracts.
- Cleaner shape: is this a chance to leave the code better than you found it?

## Writing

You are a high-level technical professional. Professional tone throughout.

- Never use em dashes
- Rarely use hyphens. Prefer correct punctuation.
- Never use "It is this X, not that Y" or "It is not X, it is Y" constructions

Reproduce first. When a conventional test is impractical, use a deterministic script or direct observation and explain the boundary. Instrument uncertain runtime behavior. Search for sibling instances of the same failure pattern.

## DRY: no compromise

Duplication is the single easiest way to wreck a codebase. Zero tolerance.

- Before writing a new function, helper, type, or constant, search for an existing one. If it exists, use it. If it is close but not exact, refactor the existing one so both callers share it.
- Never copy a block of code "just for this one case". Never re-declare a type that already lives somewhere else. Never inline a constant that is already named.
- If two pieces of code do the same thing with minor variation, the variation belongs in a parameter, not in a second copy.
- When migrating or refactoring, delete the old path completely. Do not leave parallel implementations "until later" unless the user has explicitly approved a staged migration.
- Inventory every caller before replacing an API. Migrate callers and delete the legacy path in the same change. A temporary adapter requires an explicit reason, owner, and removal condition.
- Subtract before adding. Remove dead paths, obsolete guards, redundant instructions, and empty references before building on the simpler base.
- A PR that introduces duplication is not complete. Fix it before moving on.

- New files: never more than ±700 lines.
- Files already over 700 lines must be refactored *before* new code is added to them. No "I'll just add this one more thing". No "it fits the pattern so it's fine". Refactor first, then add.
- If a function grows past ~150 lines, break it up. Long functions hide duplication and kill readability.

## Principles

# TLDR

## Channels are separate databases

One Postgres server, one database per channel. The channel rewrites the database path.

| channel | home | database | ports |
| --- | --- | --- | --- |
| stable | `~/.transport-matters` | `transport_matters` | 8787/8788 |
| preview | `~/.transport-matters-preview` | `transport_matters_preview` | 8797/8798 |
| dev | `~/.transport-matters-dev` | `transport_matters_dev` | 8807/8808 |

Canvas runs preview. CLI defaults to stable. They do not share rows.

## Inventory is keyed by executor id

Each home mints its own `executor-id` on first use. `local_executor_id()` reads the resolved
channel's home. Query a database with the wrong channel's id and you get an empty inventory,
not an error.

Old ids left in a table are orphans from a wiped home. Harmless.

## Harness state has three refresh triggers

No harness has a refresh policy of its own. One implementation answers three triggers, all
scoped to the answering channel, all swallowing failures into the log.

    backend start    run_startup_refresh, once per start, staleness bound
    manual refresh   POST /v1/harnesses/refresh, harnesses(refresh=true), harnesses refresh
    version change   the launch gate saw a version the stored observation lacks

The staleness check enumerates nothing when the stored rows already match the installed
version, adapter revision and release attribution. A manual refresh bypasses it whole: asking
to look again is the statement that the stored rows are wrong. The launch trigger persists the
new observation in the gate's own transaction and queues one forced enumeration for that
harness in a background thread, so `ResolvedTarget.installed_harness_version` and the run's
compatibility facts name the same version. The worker owns its event loop and database pool
and runs the same single harness refresh, including authentication. Grok's combined probe
therefore runs on all three triggers and refreshes authentication even when targets are current.

The launch trigger fires when the observed version changed **or** the stored target rows do
not describe the installed version. Eligibility derives from the work product, never from a
marker: the observation is persisted whether or not the worker lands, so a pass that was never
started, died with its process, or raised stays owed and is retried on the next launch. Only a
complete enumeration converges; a partial fallback retains rows at the previous version by
contract and deliberately stays eligible, and that retention is never rewritten to silence a
retry. One pass runs at a time per database, executor and harness, so repeated launches queue
one writer rather than a pile. Force a pass in code:

    refresh_harness_state(ExecutorEvidenceStore(url, pool), force=True)

## A catalog answer carries what it proves about absence

    complete   the primary catalog: the vendor's offering, so an omission retires a model
    partial    the fallback catalog: it adds and updates, and can never retire

Codex reads `codex debug models` first, a credential free catalog GET that costs no tokens and
is the only place a model released after the binary shipped appears, and falls back to
`--bundled`, the catalog frozen into the binary. `visibility` is the vendor's picker policy and
is never read: explicit selection resolves a hidden slug, so importing it would recreate a
hidden model class inside Transport Matters.

A failed catalog run is typed, not `None`. `ModelEnumerationFailed` names `timeout`,
`nonzero_exit`, `invalid_output` or `execution_failed` per attempt and nothing else, and when
every catalog fails no target row moves. Enumeration owns a 30s budget separate from the 5s
authentication timeout, because the claude catalog measured 4.7s against that 5s and silently
preserved stale rows when it tripped.

## No release means not launchable; no targets does not

`_refresh_harness` returns early when the harness has no embedded release, before the probe that
enumerates models. Result: an observation row with the fallback revision, zero target
observations, and a launch view reporting `compatibility_release_unavailable`. The missing
release is what withdraws the harness. Refresh once the release lands.

Zero targets on their own never do. An installed, enabled, launch capable harness whose
enumeration is absent, stale or failed is offered with `models: []`, because a launch that
leaves model selection to the harness still works. Nor does a harness version change drop a
target: rows are retained by the store, `installed_harness_version` and
`target_observation.harness_version` are two authorities on `ResolvedTarget`, and only a
complete snapshot retires a row (#632).

## Bundles read the live run, not the store

`harness_version` comes from `read_compatibility_facts(turn.storage_dir)`. A stale store changes
what the launch view offers. It never reaches the evidence.

## Blessing is a range, verification extends it

`docs/HARNESS-COMPATIBILITY.md` owns this contract in full. What follows is the journey.

A Transport Matters release blesses a version range per harness and ships the reference
request schema captured at its **baseline version**, the one version a certification run
actually proved. The blessed ceiling can sit above the baseline: `blessed_ceiling` returns
`maximum_version or baseline_version`, and a declared maximum records versions the comparator
cleared rather than versions a run observed. The top of a range is the extent of the blessing,
never the source of the evidence. Closing that gap is what comparison is for.

An installed harness sits in one of three states.

| installed version | behaviour |
| --- | --- |
| below the floor | prompt to upgrade. Running anyway is allowed and known degraded. Capture is best effort and overlays may be degraded. |
| inside the blessed range | supported. Nothing to decide. |
| unknown | compare it against the shipped reference and decide. |

Nothing is ever blocked. An unknown version is not a reason to refuse a launch, and it is not
a reason to refuse a comparison. It is the reason to run one.

The comparison is lazy. It fires when a model is actually launched, never eagerly across every
model of a harness. Launching `claude opus` at an unknown version captures opus at that version
and compares it to the reference.

## Request shape is a cell dimension

    first-turn   the delivery's own request: message items only
    tool-turn    the request carrying one tool call and its result back

`RequestShape` in `baseline_plan.py` is a coordinate of every cell, current pointer, attempt
record, publish plan cell, release reference and support verdict. Two shapes of one model are
two cells and never peers in a cohort. A publication binds both shapes of every captured
model; a release published before the dimension existed carries first-turn references only,
and the launch gate compares what that release carries without refusing the shape it lacks.
The resolver folds one model's verdicts across shapes: degraded anywhere is degraded.

The tool-turn prompt asks the harness to use bash to print the current datetime, so the
harness's own shell tool is the deterministic thing that gets called and no stub tool is
declared. The delivery id names the first request; the tool-turn request is the one request
in the delivery's run that carries a tool result, accepted once the provider answered it
without asking for another tool. More than one tool call, result, or result request fails the
probe. `provider_requests_per_probe` is how the publish plan prices the extra request.

## The envelope is a second schema of the cell

    body schema      the request body, minted under the provider's profile
    envelope schema  the transport, minted under `http-envelope`

`transport_envelope.project_request_envelope` reduces one probe's `transport.json` to names:
protocol, method, host, path, query parameter names, header names and content encoding tokens,
each spelled as a key with `true` beneath it so the comparator sees a value change as a
property change. Values never enter the projection. A name `transport_redaction` would redact
is dropped, not redacted, so an auth header arriving or departing is invisible by design.

The projection is stored per probe (`ProbeEvidence.request_envelope`, artifact version 11),
and `GateProjection.envelope_schema` is minted from the three projections through the one
minter every body schema goes through. A release reference carries `envelope_schema` beside
`request_schema`; `assess_support_state` compares both when both sides carry one and folds
them, degraded anywhere is degraded, with `compared_profiles` naming what answered. A
reference published before the envelope existed carries none and the gate compares the body
alone, the rule #604 set for a missing request shape. A bundle at version 10 loads with no
envelope and mints no envelope schema.

Coverage for the envelope lives in `ir_coverage_tables` under `HTTP_ENVELOPE`: `/headers` is
read by name. The named consumers cover `anthropic-beta`, `anthropic-version`, `session-id`,
`thread-id`, `x-codex-turn-metadata` and `x-grok-turn-idx`; every other header is unmodeled.
`/method`, `/host` and `/path` are `value_set` positions, so a routing coordinate departing
degrades. Query, protocol and encoding are recorded and never degrade.

## Support state and its cause are separate keys

    state:    unknown | blessed | degraded
    findings: missingProperties[...] | additionalProperties[...]

A missing property means degraded. Additional properties stay blessed and record the finding.
Neither means blessed with no findings.

`unknown` is a real state, never null: neither a complete local assessment nor exact
publisher coverage exists for the model at this version. It carries a reason, and only
`verification_pending` carries a phase (`queued` | `running`); absence of any capture
evidence is `provenance_unavailable`. A model the release does not reference is judged
against every sibling reference of its route, body profile and shape, exact reference
first and exclusively when one exists; all siblings compared and none blessed is
`degraded` with reason `no_compatible_reference` and no invented finding. Verdicts
persist under candidate identity, reference identity is provenance, and a runtime
blessed newcomer never becomes a reference for another model. An already referenced
model inside the blessed range inherits the publisher's blessing and spends nothing; an
unreferenced model is captured on first launch whatever the range says, and
reconciliation of local evidence runs under the cell lock and precedes the quota gate.

The capture binds its own route. Each probe's exact client environment answers the
harness's own status command for the authentication method (never inferred from key
presence), the stored envelope answers the transport, and the bundle folds the three
probes only on full agreement (artifact v12, `capture_attribution`). One shared resolver turns that into a
`route_id` against the pinned release, on provider, transport family and authentication
family together (the descriptor declares both provider spellings, codex captures parse
under `codex` while its route says `openai`), and the writer, the reader, runtime reuse
and publication binding all use it. Anything short of one unique match binds nothing:
publication refuses the evidence, and a capture that lands unattributable records that
gap on its attempt, so it reports `provenance_unavailable` and is never paid for twice.

A rename needs no detection of its own. It is a known property going missing, which is already
degraded whether or not something new arrives beside it.

A relocation is reported as the move it is. When a departing property or branch reappears
identical under the same key elsewhere, the departure becomes one `relocated` finding naming
`moved_to`, and it still grades and degrades as the removal it contains. Finding pointers carry
one bracketed token per array descent (`/messages/[role:literal:user]/content/...`) so two
positions can be told apart. Coverage is declared without them, except where one branch has a
different consumer: an exact selector with tokens wins over the generic position.

A discriminator change is reported at the discriminator. When every item of an array loses or
gains the property its branch tag is built from and nothing else differs, the comparator says so
at each branch's `/type` (or `/role`). It does the same for one branch changing its tag while the
other branches still match. Coverage then answers for the position that actually changed.

`degraded` means overlay fidelity is compromised. It carries that one meaning everywhere,
including an unsupported old version. `blessed` is its converse. Additional properties are not
degraded because the overlay is not wrong, only incomplete.

`DriftOutcome` (`EXACT` / `DEGRADED` / `BREAKING`) is a property of one comparison. The support
state is a property of a version. They share a word and are not the same axis. The comparison
feeds the state; the state is what an operator sees.

## The second hop is declared

    request schema  ->  IR  ->  overlay

The real question is whether an overlay degrades. `ir_coverage` declares the second hop per
profile: every pointer is `modeled`, `normalized` or `unmodeled`, and a verdict degrades only
on a loss at a position some consumer reads. Consumers live on both sides of the wire: an IR
field (`ir_target`, checked against `ir.py`) or a browser reader of `provider_extras`
(`ui_target`, checked against the TypeScript source; the inspector reads `extras.thinking`
and `extras.output_config`). An unclassified position still degrades: the presumption is
narrowed, never removed.

`normalized` absorbs exactly the declared kind pair the adapter provably collapses (the
string shorthand on `system` and `messages[].content`) and nothing else. Structure departing
with a kind change is reported missing in its own right, so an absorbed kind change can never
hide a modeled descendant. IR to overlay is the hop that still remains.

The `additionalProperties` findings are the queue for that work: wire fields TM does not model.

The comparison itself is built, whatever the chain above still lacks. Releases ship reference
schemas: `claude-2.1.241-r2` carries ten, one per target, which is what a launch at an unknown
version is compared against.

The comparison is directional. `assess_support_state` fixes the reference on the left and reads
the verdict off that one direction, so a candidate that merely adds a field never answers for the
reference's lack of it. The worst-of-both fold survives where it belongs, in the cohort gate:
`baseline_comparison.compare_model_pair` runs both directions and takes the worse, which is right
for two models of one harness because peers have equal standing.

## Verification queues work before it spends

`baselines/verification-queue` belongs to one channel. Admission pins the release,
version, route, required shapes, binary and quota owner; repeated launches join one
request and distinct models queue separately. Startup discovers pending work without
another launch. Admission never increments the provider attempt count.

Two kernel-held slots bound physical capture across backends. A deadline starts only
when a slot is acquired. Cancellation leaves the slot with the physical worker until
it exits. Reconciliation runs under the cell lock before quota, and a deferred cell
returns to the back of the queue. The resolver reports queued or running work as
`unknown` with `verification_pending` and its phase.

`GET /v1/harnesses/{harness_id}/support-verdicts` reads retained evidence independently
of catalog membership, with `model`, `route`, `version` and `release` filters. Retirement
removes a picker target while preserving its verdict, and a diagnostic read restores
nothing to the picker.

## A run that captured nothing says so

    captured_nothing = turns >= 1 and exchanges == 0

`roster()` carries `capture: {turns, exchanges, captured_nothing}` on every item.
`project_roster` derives it from two reads `_roster_snapshot` already gathers: primary turn
count per run from `event`, and exchange count per run from `wire_exchange` under
`_WIRE_EXCHANGE_OWNER_PREDICATE`, so a subagent track is counted the way the inspector lists
it. Nothing is stamped at exit. Exchange persistence is asynchronous to harness exit, so a
fact written at release could record a false zero and never correct it; a fact derived at
read time heals on the next roster read and covers every run already in the database.

The predicate is turns, not time. A run that took no turn legitimately captured nothing and
reports false. The fact is advisory and never fatal: it points at a harness release moving
its endpoint, a redirect override that could not be placed, a matcher that stopped admitting
a flow, or an operator config that repoints the client. It makes the escape visible; it does
not close it.

## An override batch is a transaction

    miss      a required operation whose target the request does not have
    shadowed  a rewrite whose target the same batch disables

`apply_overrides` applies the batch in priority order and returns the original IR on any
miss. Every audit entry then reads `applied: false` and a warning names the misses. A
rewrite shadowed by a disable of its own target (`tool_toggle` over `tool_description`,
`system_part_toggle` over `system_part_text`, `message_block_toggle` over `message_text`)
is audited as not applied and is never a miss, so disabling a tool that still carries an
edited description keeps working. Message sanitization runs only when the batch carries a
message operation, so an empty override set is byte identical.

Serialization is the last step that can fail between the pipeline and the wire.
`prepare_outbound_request` wraps `outbound_request_if_changed` and on any exception returns
the original IR, no audit and no bytes, so the flow state records what actually went out.
The HTTP handler, the Codex WebSocket handler and breakpoint release all go through it. An
edited Forward payload skips it because the route already serialized it and answered 422 on
failure. Pass Through defers serialization to breakpoint release so an unchanged request keeps
its original bytes and a failure forwards those bytes.

## Absence is not death, a lock is

    runtime_id   one gateway process, minted at boot, stamped on every managed run-started row
    lease        pg_advisory_lock(run_runtime_lock_key(runtime_id)) held for the gateway's life

A gateway inventory answers only for the runs its `RunManager` holds. The startup sweep
and the operator `close` reap a row absent from the answering gateway only when the row
is stamped with that gateway's `runtime_id`, or when `pg_try_advisory_xact_lock` on the
foreign runtime's key acquires, which proves that gateway's session ended. A held key is
`held`, an unstamped row is `unowned`, and neither is ever reaped from absence. Two
backends on one channel database therefore cannot reap each other's live runs (#610).

A synthetic exit (`exit_reason: reaped`) is the only retractable exit. When the owning
gateway later lists the run, convergence sets `retracted_at` in place; Activity reads only
standing exits and rebuilds an exited actor, so roster, watch, prompt preflight and Canvas
follow. The next real exit replaces the retracted row through the one upsert. The primary
key is unchanged so an older backend still running keeps inserting.

Losing the lease keeps every PTY alive. The gateway reacquires the same `runtime_id` with
backoff and answers `runtime_unleased` (503) to new managed creates until it holds the key.

## A canvas run's proxy is a binding

    per-run      the CLI's embedded launch: one mitmdump child, liveness is the process
    shared       a run prepared over the capture RPC: one reverse listener on the channel
                 backend's SharedProxyManager, liveness is the binding

Both walk `prepare_captured_run`. The shared path differs in two parameters only:
`supervisor_factory` yields a `SharedProxyRegistration` and `proxy_starter` registers the
attempt's listener instead of spawning mitmdump (`shared_proxy/registration.py`). Port
stepping, readiness retry, identity, prompt delivery arming and grant persistence are the
one path. The binding is built from the launch environment the harness is spawned with,
the same carrier the per-run addon reads through `Settings`; parity is a test.

`alive` is "the manager still holds the binding". The manager's mirror survives a
subprocess restart and is replayed into the new process, and the monitor loop retries
forever with backoff, so a restart in flight is never run death. The gateway's
`CaptureHealthMonitor` tears a run down the first time it sees `alive: false`, which is
why the process is not the liveness signal. A binding leaves the mirror only through
release or manager shutdown.

When the shared proxy failed to start, `create_capture_registry` falls back to the
per-run path and logs it once. Overrides reach canvas runs because `manager.by_run_id`
now lists them.

## Breakpoints live where the flow pauses

    downstream   arm, disarm, status, paused, release, drop, re-audit: control requests
                 the subprocess answers against its own `breakpoint` state
    upstream     the addon's inspector broadcasts, relayed on `tm_events` as
                 `inspector_event` and re-emitted by the owning backend's bridge

The inspector's routes dispatch local first, then through the shared proxy, so the
CLI's embedded launch and a canvas run answer the same routes. Arm is scoped by run:
`bp.arm(run_id)` pauses that run's next request and no other run's on the same
proxy, and the pause serializer is one lock per run, so a flow held on codex never
blocks a pause on claude. An override edit at a shared-proxy breakpoint previews
through the proxy's own re-audit after the store is synced, and a preview lost to a
control error never fails the mutation.

Upstream, an event that fits the NOTIFY cap rides whole. `paused` rides as a doorbell
because it carries a request body, and the bridge pulls the flow's live detail. Any
other event over the cap (an `exchange` behind an edit carries the audit of every
applied override) is parked in the subprocess and rides as a reference the bridge
pulls once over the control channel; the inspector's Forward waits for that exact
exchange event, so it is never dropped. Every backend on the channel database hears
every relay, and the bridge re-emits only for runs its manager holds.

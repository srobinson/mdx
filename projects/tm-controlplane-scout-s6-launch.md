# S6 scout: launch + manage verbs (reuse map + adoption risk)

Read at main `38e9f79` (S1-S5 merged). Tree pristine, no repo writes. Spec: CONTROLPLANE.md "Launch" (126-134) and "Manage" (136-139).

Architecture fact that frames everything: the PTY executor is the Node gateway. `prepare_captured_run()` runs in the Python process, but the process that spawns and owns the client PTY is the gateway's `RunManager`, which drives `prepare_captured_run` through the loopback capture RPC. The launch verb therefore reuses the seam one level up: it calls the gateway `POST /v1/runs`, not `prepare_captured_run` directly.

## 2. Risk map: adoption (the novel piece)

### How a UI-spawned run reaches the canvas today
1. Canvas action (`www/packages/canvas/src/model/canvasActions.ts createCapturedRunActions`) creates the pane record locally (`spawn.ts createCapturedRunRef` → `capturedRunStore` runKey→runId) and calls `createCapturedRun` (`@tm/core transport.ts` → `POST /v1/runs`).
2. The pane attaches over `WS /v1/runs/{id}/terminal` (proxied `run_proxy.py:426` → gateway `runtimeRouter.ts:206`).
3. Pane/run state persists in `capturedRunStore` (localStorage); on route mount `SessionCanvasRoute.tsx:72-96` runs a **prune-only** reconciler: `reconcileCapturedRuns` looks up each persisted runId (`getRun`), drops panes whose run is not `STARTING|RUNNING` (`isAttachableRun`, line 158), 3s timeout, transient failure keeps state.

So the canvas only ever renders runs **it created or persisted itself**. Nothing scans for foreign runs.

### What exists toward adoption
- The canvas already consumes the activity stream: `useWorkspaceActivityStream` → `runVitalsStore.applyFrames` (`SessionCanvasRoute.tsx:43-47`). This is exactly the trigger stream the spec names.
- The activity wire run already carries `launch_kind: string | null` (`contract/src/activity/wire.ts:74`).
- `GET /v1/runs` (list) and `getRun` exist for the retry/liveness checks.

### What is missing (must-build)
- **The reconciler itself**: nothing watches activity frames for runs absent from `capturedRunStore` and registers panes. `reconcileCapturedRuns` is the inverse direction (prune known, not adopt unknown) and runs once at mount, not on stream events.
- **The `launch_kind` discriminator value**: kinds are a closed set `("canvas", "detached")` in **four coupled places**: `run_lifecycle_contracts.py:7` tuple, `LaunchKind` StrEnum (`session/models.py:57`), a **DB CHECK constraint** (`0007_run_lifecycle_event.py:46 run_lifecycle_launch_kind_ck`), and the TS closed set `launchKinds` (`packages/activity/src/domain/runActivityEvent.ts:8`) whose row coercion **throws TypeError on unknown kinds** (`postgresRecords.ts:314-318`). Adding `service` (or `launched`) requires a new migration altering the CHECK plus the TS mirror + fixtures. Deploy-order hazard: a `service` row written before the TS reader knows the kind crashes the activity adapter, so readers/constraint land with or before the writer.
- **launch_kind threading**: it is stamped in two places today, neither parameterized: `capture_rpc.py:289` hardcodes `LaunchKind.CANVAS` into lifecycle events for every gateway-spawned run, and the detached CLI path stamps `DETACHED` via `_with_run_lifecycle_launch_kind` (`captured_run.py:107`). The launch verb needs a `launchKind` field threaded `POST /v1/runs` body → `RunManager.create` input → capture RPC request → `_CaptureRunFacts`/launch_fields, defaulting to `canvas` so existing callers are untouched.

### The race, and retry-until-adopted-or-gone
`RUN_STARTED` is emitted inside `prepare_capture` (`capture_rpc.py:174`) **before** the gateway has even spawned the PTY, so the run can appear in activity frames while: (a) the gateway spawn subsequently fails (best-effort rollback emits `RUN_EXITED(error)`, RunManager.ts:333-343), (b) the run is `STARTING` and `attach` would 409 (`run_not_attachable`, RunManager.ts:372). Adoption must therefore be a retry loop, not an event handler:

- On each activity frame (or a short interval while any candidate is pending): for every run with the service launch_kind whose run_id is not in `capturedRunStore`, attempt adoption: `getRun(runId)` → if `STARTING|RUNNING`, register pane record + store entry (the same shape `createCapturedRunActions` builds) and let the pane's normal attach/retry take over; if 404 or terminal state, mark gone and stop.
- "Gone" is observable two ways and both must end the loop: run vanishes from activity frames (`_apply_activity_snapshot`-style disappearance) or `getRun` returns 404/non-attachable. The existing mount-time prune reconciler then covers restarts for free, since adopted panes persist like any other.
- Idempotency guard: adoption keyed by runId against `capturedRunStore` membership so re-delivered frames and multiple frames per run cannot double-register; note two open canvas windows on the same workspace will each adopt (same as today's multi-window semantics for persisted panes — flag for the owner, not solvable canvas-side).

## 3. Quality map (dup/dead/boundary risk in the launch/spawn area)

- `packages/runtime/src/service/RunManager.ts` is at **692/700 LOC**. Any S6 change there (the no-text interrupt extension is the one candidate) trips the refactor-before-add rule. Natural split: the input-delivery cluster (`validRuntimeNudge/validRuntimeInput/hasTerminalControl/BREAK_SEQUENCE_BY_HARNESS/deliverInput/enqueueInput/submittedInput`) into its own module.
- `run_proxy.py` at 582 LOC gains two typed methods; fine, but the S5 review already flagged `deliver_watch_nudge` + `/nudge` as a redundant parallel of `deliver_input` — if S6 adds methods, folding the nudge leg into `deliver_input(mode="nudge")` at the same time keeps the file one primitive smaller instead of three-primitives-larger.
- `POST /v1/runs` on the Python side is origin-gated (`require_http_origin`, `run_proxy.py:410`) because it is browser-facing; the control-plane service calling the gateway directly (as `deliver_input` does) bypasses that correctly — do not route the verb through the Python REST forwarders.
- `capture_rpc.py` hardcoded `LaunchKind.CANVAS` becomes wrong the moment a second gateway-spawn intent exists; parameterizing it is the root fix, a service-side override would be a bandaid.
- Workspace scoping: `prompt` gates targets by the principal's workspace via an activity snapshot (service.py:144-177). `launch(workdir)` has no equivalent structural gate — the gateway create path will happily spawn in any directory. Policy gap, not code gap.

## 4. Plan

### Decisions needed (6)
1. **Adoption mechanism**: canvas-side retry reconciler driven by the existing activity frame stream + `capturedRunStore` membership, adopting service-kind runs while attachable and abandoning when gone (shape in §2). Alternative rejected: server-push pane registration (no such channel exists; canvas owns pane state).
2. **launch_kind value + threading**: new kind (`service`) through contracts tuple, StrEnum, migration altering `run_lifecycle_launch_kind_ck`, TS `launchKinds` + fixtures; parameterize `capture_rpc.py:289` and the `POST /v1/runs` body. Deploy order: constraint + readers before the first writer.
3. **first_prompt readiness**: recommend activity-signal wait — poll/stream until the target leaves `starting` (bounded, e.g. N seconds), then `deliver_input(mode="nudge")` with the standard envelope; receipt reports `first_prompt: delivered|failed|skipped`. Alternative: blind retry on `run_not_running` (cheaper, but delivers into a harness that may not be listening yet).
4. **Workdir scoping policy**: restrict `launch(workdir)` to the principal's workspace (mirror prompt's scoping) or allow any path. Spec is silent; security posture says restrict.
5. **No-text interrupt shape**: extend `deliverInput`/`/input` (text optional iff interrupt) vs. a separate break-only mode. Either way RunManager.ts must be split first (692/700).
6. **Receipt + audit shape**: launch returns `{run_id, status, first_prompt?}` and audits one `control_plane_action` (verb=launch, targets=[run_id]); manage verbs audit per-target like prompt. Builder placement: sibling functions beside `prompt_action`.

### Steps (bound to the reuse map)
1. Node: split RunManager input cluster (mechanical, no behavior); add optional-text interrupt to `deliverInput` + `/input` route.
2. launch_kind `service`: migration + Python contracts/enum + TS domain/fixtures + parameterize capture RPC and `POST /v1/runs` body (default `canvas`).
3. Python control plane: typed `create_run`/`terminate_run` on `RunRouteProxy` + `ControlPlaneGatewayPort`; service verbs `launch`/`stop`/`interrupt` on `ControlPlaneService` reusing `_require_director`, envelope, audit-or-die; REST routes + MCP tools per existing template.
4. first_prompt: readiness wait per decision 3, delivered via `deliver_input`.
5. Canvas: adoption reconciler per decision 1 (new module under `www/packages/canvas/src/model/` or `infrastructure/stream/`, consuming the frames `SessionCanvasRoute` already subscribes to).

### Tests + gates
- Python: colocated unit tests per module; integration `api/tests/integration/` sibling to `test_controlplane_prompt.py` for the launch verb round trip. Gate: `just check` and `just test` verbatim.
- Node runtime: `pnpm --filter @tm/runtime test` (deliverInput no-text interrupt, create launchKind threading, router contract).
- Canvas/structural: full `pnpm --filter @tm/shell test` (adoption touches stores + persistence; structural-PR rule applies). Persistence caution: adoption writes into `capturedRunStore` — persist-old-snapshot-then-rehydrate test required for any store shape change.
- Migration: alembic upgrade against a store containing old kinds; TS `postgresRecords` fixture for the new kind (TypeError guard is the failure mode).

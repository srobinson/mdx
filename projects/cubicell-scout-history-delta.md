# Cubicell history delta: reuse map and plan

Scout beat for the `perf/history-delta` slice. Read only, against `main` at `77b7795`, clean tree. Input evidence: `~/.mdx/projects/cubicell-scout-durability-perf.md` (221.88 KB average history row rewrite per authored edit on the 33 State document; N whole-Workbench diffs on main per edit).

## Reuse Map

- Reuse: `src/state/historyDiff.ts:createHistoryDiff` and `src/state/historyDiff.ts:applyHistoryDiff`. The delta primitive already exists; one adjacent Workbench pair per edit replaces the N-pair chain in `src/state/historyDiff.ts:encodePersistedHistory`. `isSafeHistoryPath` and the `fast-json-patch` wrapper in `src/shared/jsonDiff.ts:createJsonDiff` come with it.
- Reuse: `src/state/documentHistory.ts` unchanged. Runtime undo and redo (`undoDocumentHistory`, `redoDocumentHistory`, `documentHistoryLimit = 100`) never read persisted history after boot; the slice is persistence-only.
- Reuse: `src/persistence/recordCodecs/localHistoryRecordCodec.ts:hydrateBranch` internals as the step validator: `historyStepOwnershipError`, `reconcileSelection`, `repairActiveStateReference`, `reconcileProjectAssets`, and the `extendPoseRevisionRegistry` conflict check all apply per step regardless of how steps are stored.
- Existing infra: `src/persistence/indexedDbSchema.ts:createIndexedDbProjectSchema` deletes every object store on upgrade, so bumping `indexedDbProjectStorageVersion` 8 to 9 is a full reset with zero migration code. `historyUserRange` is the range-read pattern for the new step key.
- Existing infra: `src/persistence/indexedDbCommit.ts:issuePromoteWrites` is the single atomic write site; the appended step row and pruning deletes slot into the same strict transaction that puts the asset snapshot, which preserves the anchor-consistency invariant for free.
- Existing infra: `src/persistence/poseRevisionRegistry.ts:PoseRevisionRegistry` plus the `poseRevisions` store (see Quality Map answer on question 3 below).
- Similar checked and rejected: `src/persistence/pendingDrafts.ts` append machinery (`appendPendingDraft`). It appends operations inside one draft row, so every append still rewrites the row via structured clone. Wrong shape; the win requires one row per step.
- Similar checked and rejected: `outbox` store as a journal. It is append-only with an autoIncrement `sequence` key (good pattern to copy for the step key), but it stores authored operation envelopes, not Workbench deltas, and the prior scout report marks it dead pending deletion. Copy its keying idea, not the store.
- None found: no existing per-step persisted journal of Workbench deltas. Searches: `fmm_search` on `hydrateLocalHistoryRecord`, `encodeLocalHistoryRecord`, `projectHistoryRecord`, `undoDocumentHistory`, `prunePose`, `poseRevisionPrune`; outline of `localHistoryRecordCodec.ts`, `projectRecordHydration.ts`, `indexedDbSchema.ts`, `indexedDbCommit.ts:issuePromoteWrites`. New code is justified only for the step record codec and the spine row; every primitive it composes already exists.

## Answers to the brief's questions

**1. Ownership.** One writer, one reader, tight seam. Writer: `src/persistence/projectRecordProjection.ts:projectHistoryRecord`, whose only production caller is `src/state/projectCommitProjectionCore.ts:compactProjectionState` (main thread, gated by `ProjectProjectionPlan.encodeHistory`). Persisted by `src/persistence/indexedDbCommit.ts:issuePromoteWrites` as `history.put` keyed `[projectId, userId, assetKey]`. Reader: `src/persistence/projectRecordHydration.ts:hydrateProjectRecords` calling `hydrateLocalHistoryRecord`, reload only. At the moment undo or redo runs, `src/state/actions/documentActions.ts` reads only the in-memory `DocumentHistory` snapshots via `src/state/documentHistory.ts:undoDocumentHistory` and `redoDocumentHistory`. The persisted record is a reload artifact, never a runtime read.

**2. Rewrite shape.** Not a snapshot per entry. One aggregate `local-history` row per `[projectId, userId, assetKey]` whose `past` and `future` are backwards RFC 6902 diff chains anchored at the present Workbench (`encodePersistedHistory` walks newest to oldest from `present`). Because the anchor is the present, every edit invalidates the entire chain; the full rewrite is structural, not an implementation accident. Bounded by count only: `documentHistoryLimit = 100` per branch, `encodeLocalHistoryRecord` slices to 100, `decodeLocalHistoryRecord` rejects branches above 100. No byte bound. Each `LocalHistoryStep` also repeats a complete `ProjectManifest`.

**3. poseRevisions.** It is a genuine content-addressed store: keyed `[projectId, revisionId]`, written append-only (`poseStore.add` in `issuePromoteWrites`; no delete or prune path exists). On reload `hydrateProjectRecords` decodes the whole store first and `materializeLibrary` resolves committed asset pose references from it, and `hydrateLocalHistoryRecord` already threads a `committedRevisions` registry. So the structural sharing a delta scheme needs already exists and no new content store may be invented. But the delta does not reduce entirely to revision ids: today the RFC 6902 step ops inline full pose payloads (the Workbench embeds `PoseRevision = Pose & ids` in `library.states[].pose`), and the registry is used only for conflict detection, not payload resolution. The correct split: the per-edit delta stays an RFC 6902 Workbench diff (cells, structure, selection have no content store), while pose values inside step ops can be stripped to revision ids and rehydrated through the registry `hydrateBranch` already receives, since every pose a history entry references was committed and therefore lives in `poseRevisions`. That stripping is a second-order compression; ship it only if the first cut leaves pose-heavy steps material.

**4. Invariants a delta scheme must preserve.**
- Depth: 100 per branch, enforced at encode and decode; append scheme must prune `seq <= head - 100`.
- Redo after branch: `pushDocumentHistory` clears `future` on every new edit; append scheme must delete step rows above the cursor when a new edit lands after undo.
- Restore on reload: both branches rebuild relative to the present assembled from committed assets plus checkpoint overlay (`resolveWorking(project, library, checkpoint, userProjectState)`). Anchor consistency holds today because the history row and the asset snapshot commit in one strict transaction; the appended step must stay inside that same transaction.
- Step-level tolerance: hydration skips individual bad steps (`rejected[]`) but rejects a branch on an invalid diff; pose id conflicts reject via `PoseRevisionConflictError`. `actionJournal` seeds from hydrated branch lengths.
- Per-step context: `activeStateId`, `selection`, `selectionSet`, `viewPolicy`, and Project manifest ride each step and are repaired on hydrate; the step record keeps `EncodedHistoryStep` exactly.
- Checkpoints: the committed asset is the checkpoint; the draft overlay only shifts the present the chains anchor to. No interaction change if the newest step always diffs against the committed present at promote time, as today.

**5. Sizing.** Smallest change with most of the win: replace the aggregate row with one appended step row per edit plus a tiny spine row, behind the existing writer and reader seams. Per authored edit this replaces a ~221.88 KB rewrite with one ~2 KB step append and a ~0.1 KB spine put, and replaces N main-thread Workbench diffs with one (two if redo ops are stored). Undo and redo promotes stop writing history bytes entirely except the spine cursor. No runtime state, reducer, or coordinator changes.

## Quality Map

- Duplication / parallel implementation: `localHistoryRecordCodec.ts:encodeBranch` wraps `encodePersistedHistory` with a synthetic `{future: [], past: entries}` history; the aggregate path must be deleted whole when the step path lands, not left beside it.
- Duplication on the wire: `LocalHistoryStep.project` repeats a near-identical full `ProjectManifest` per step (about 100 copies per branch on a large document). Step scheme should store the manifest only when it differs from the prior step; `entryProject` already handles the null fallback.
- Boundary / design issue: history encoding is the one record projection that runs on the main thread (`compactProjectionState` before the projection worker) while all other records project in the worker. The step scheme shrinks the main-thread share to a single adjacent diff.
- Dead code / obsolete path: `outbox` store and `HydratedProjectRecords.outbox` are dead per the durability scout report; separate slice, do not entangle, but the step-store keying may copy its sequence pattern.
- Grooming recommendation: refactor during. `localHistoryRecordCodec.ts` (271 LOC) becomes the step codec in place; `projectRecordHydration.ts` (538 LOC) stays under threshold. No pre-refactor required.

## Plan

- Decision needed: must redo survive reload? Backward undo ops alone cannot rebuild the `future` branch from an older present. Today redo survives. If yes, each step stores both `undoOps` and `redoOps` (roughly 2x step bytes, still ~2 KB scale). If no, store `undoOps` only and drop `future` at hydration; halves bytes and simplifies the codec. Owner call.
- Proposed steps, bound to the reuse map:
  1. Wire: add `historySteps` store keyed `[projectId, userId, assetKey, seq]`; shrink `history` to a spine row `{head, cursor}` under its existing key. Bump `indexedDbProjectStorageVersion` 8 to 9; `createIndexedDbProjectSchema` already resets, no migration.
  2. Codec: new step record = `EncodedHistoryStep` + seq + optional manifest, encoded from one `createHistoryDiff` pair; keep `decodeLocalHistoryRecord` validation pieces (`historyStepOwnershipError`, selection and reference repair, pose registry conflict check) as the per-step decoder. Delete the aggregate record type and both branch chain functions.
  3. Projection: `projectHistoryRecord` (and its `compactProjectionState` gate) emits the one appended step plus spine instead of the aggregate; `prepareStorageRecords` stringifies and fingerprints only those.
  4. Promote: `issuePromoteWrites` appends the step, deletes rows above cursor on branch, deletes rows below `head - 100`, puts spine; undo and redo promotes put spine only. All inside the existing strict transaction.
  5. Hydration: `hydrateProjectRecords` range-reads step rows (pattern of `historyUserRange`), walks from present with `applyHistoryDiff` to rebuild `DocumentHistory`; `rejected[]` semantics preserved.
- Tests and gates:
  - `pnpm vitest run tests/projectRecordCodecs.test.ts tests/documentHistory.test.ts tests/historyDiff.test.ts tests/poseRevisionIntegrity.test.ts --project unit` for codec and invariant coverage; extend `projectRecordCodecs.test.ts` to the step codec and delete aggregate cases with it.
  - `pnpm vitest run tests/cubicellStorePersistence.test.ts tests/committedStorePersistence.test.ts tests/cubicellStoreDurabilityRecovery.test.ts --project unit` for reload and recovery.
  - `pnpm test` full unit gate; `pnpm test:browser` for the storage record browser driver.
  - Controlled-red proofs: depth prune at 100, redo-branch drop after undo-then-edit, and hydration rejection of a corrupted step must each fail before the guard and pass after.

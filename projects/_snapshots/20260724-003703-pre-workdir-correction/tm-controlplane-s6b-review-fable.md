## Brief priorities, answered

1. **Persistence / data-loss: CLEAN.** `adoptRun` writes `{provider, runId}`, a strict subset of the existing v4 `CapturedRunRecord` shape (`minimized?` optional). No shape change, so no version bump was needed and none was made. `migrate`/`partialize` untouched. The diff carries a genuine old-snapshot test (`capturedRunStore.test.ts` "rehydrates a pre-S6b v4 snapshot...") that loads a stored v4 payload carrying `minimized: true` plus `oscColorReplies`/`bypassPermissions` and proves preservation alongside a new adoption. Rehydrate does not wipe. This is exactly the persist-old-snapshot-then-rehydrate gate the house rule demands. The builder got this right.
2. **Feedback loop: BOUNDED but one terminal transition is wrong (blocker below).** Both terminal states are reachable; backoff is `retryDelaysMs[attempts-1]`, max `retryDelaysMs.length + 1` attempts (5 by default, ~3.75s span), verified correct by tests including timer-count-zero. No infinite loop is possible. Idempotency is solid at three layers: reconciler `candidates` map (terminal entries never re-attempt), `hasRun` against the persisted store, and `adoptRun` dedupe by runId; pane dedupe by runKey across panes and docked. Repeated frames and reconnect snapshots cannot double-adopt (route test proves single `/v1/runs` lookup across duplicate snapshots).

## Blocker

**B1. A 404 during the launch race marks the run permanently "gone"; the retry ladder never fires for the exact race it exists for.** `capturedRunAdoption.ts` `attempt()`: `getRun` returns `null` on 404 (`transport.ts:471` — only non-OK non-404 throws). `attachableWorktreeId(null)` returns null → `finish(entry, "gone")` on the FIRST attempt. Only thrown errors reach `scheduleRetry`. Once "gone", `acceptCandidate` short-circuits on the existing entry forever — the run keeps appearing healthy in every later snapshot and is never adopted for the route lifetime.

The race is near-structural, not exotic: RUN_STARTED is emitted inside `prepare_capture` (`capture_rpc.py:187`), but the gateway registers the run in `RunManager.createNew` only AFTER `prepareCapture` returns and the PTY spawns (`RunManager.ts` register at the end of `createNew`). The activity frame can reach the canvas while `GET /v1/runs/{id}` still 404s. CONTROLPLANE.md ("retries until the run is adopted or gone") and the locked design both promise retry through exactly this window. The unit test `["missing", null] → gone` bakes the wrong contract in.

Fix shape: distinguish a successful lookup returning a terminal/mismatched run (definitive gone) from a 404/absence (schedule a bounded retry through the existing ladder); let the applySnapshot vanish path remain the authority for "left the activity stream". One-line change in `attempt()` plus flipping that test case. Verdict: CONFIRMED.

## Majors

**M1. The pre-existing prune reconciler now destroys adopted runs on the same 404.** `findStaleCapturedRunKeys` (`SessionCanvasRoute.tsx:167-178`): a null `getRun` flows into `!isAttachableRun(null)` → stale → `dropRun` + `dropCapturedRunPane`. Thrown errors are kept (the `.catch` guards them) but a 404 is not. Adopted service-run records now live in the same store, so a route remount landing inside the registration window (canvas reload while a director launches) deletes the mapping AND the pane; the fresh adoption reconciler then re-looks-up, 404s again, and B1 finishes it. Pre-existing code, but this PR extends its blast radius to runs the canvas does not own. Same fix family as B1: absence during a launch window should not be treated as terminal on one sample. Verdict: PLAUSIBLE (mechanics confirmed; trigger needs remount timing).

**M2. `hasRun` fast-path assumes mapping ⇒ pane; a store desync leaves a live run invisible forever.** `acceptCandidate` marks a candidate "adopted" when `capturedRunKeyForRunId` finds the runId, without checking a pane exists. The run mapping (`capturedRunStore`) and panes (`canvasStore`) persist under separate storage keys and are updated in separate non-atomic writes (the prune path itself does `dropRun` then `dropCapturedRunPane` as two store commits). If they diverge (partial persistence, interrupted prune), the reconciler classifies the run adopted, `adoptCapturedRun` is never invoked, and the live service run has no pane for the route lifetime. Cheap fix: route the fast-path through `adoptCapturedRun` too — it is already idempotent and pane-aware (`capturedRunPaneId` check), making `hasRun` unnecessary as a separate dependency. Verdict: PLAUSIBLE.

**M3. Closing an adopted pane terminates a director-owned run; no ownership marker exists to even ask the question.** `stopRun` on explicit KILL POSTs `/terminate` for any record with a runId. Adopted records are shape-identical to locally-spawned ones, so the canvas close affordance kills a run the director launched and may still be driving. CONTROLPLANE.md says adoption "registers the pane on the human's canvas" — it is silent on whether the human closing that pane should destroy the run. The earlier design notes intended `launchedBy`/origin lineage on RunView, which would carry the answer. This needs an explicit product decision (terminate vs detach-only for adopted panes), and the persisted record or ref needs the marker either way. Verdict: PLAUSIBLE (design gap, not a coding slip).

## Minors

**m1. Attachability predicate duplicated.** `attachableWorktreeId` inlines `state !== "STARTING" && state !== "RUNNING"` while `isAttachableRun` (`SessionCanvasRoute.tsx:180`) is the canonical predicate wired in the same route. The load-bearing "what counts as a live run" rule now has two definitions pointed in opposite directions (prune vs adopt); if the state set grows, they disagree and produce adopt-then-vanish flicker. Share one predicate. CONFIRMED.

**m2. Lookup-with-timeout duplicated.** `attempt()` hand-rolls AbortController + `setTimeout(abort)` + `Promise.race` with `CAPTURED_RUN_ADOPTION_LOOKUP_TIMEOUT_MS = 3_000`; `reconcileCapturedRuns` in the same PR's touched route has the identical wrapper with its own `CAPTURED_RUN_RECONCILIATION_TIMEOUT_MS = 3_000`. Only two such sites in www/packages and they shipped side by side. One shared abortable-lookup helper, one constant. (Note: since `getRun` forwards the signal to fetch, the `aborted` race promise is redundant for the real dependency — the signal alone suffices; the race exists to satisfy signal-ignoring test mocks.) CONFIRMED.

**m3. Spawn dance now triplicated.** `labelFor` → `set paneCounters` → `createCapturedRunRef` → `spawnPane` appears in `addCapturedRun`, `continueSession`, and now `adoptCapturedRun`. The variation (focus, runKey, target, continuation) belongs in one internal `spawnCapturedRunPane` helper. Two copies predate the PR; S6b added the third rather than consolidating. Related: new `capturedRunPaneId` duplicates the panes+docked traversal (including the `entry.ref` / `entry.record?.contentRef` dual check) that `dropCapturedRunPane` already performs. CONFIRMED.

**m4. Vitals lifecycle regression + split reconciler lifecycle.** The cleanup effect moved from unmount-only (`[]`) to `[activityWorkspaceId]` and also fires eagerly when the id is empty. Any mid-session id transition (launch resolution differing from `/api/meta`, transient query flip to `""`) wipes `runVitalsStore` and disposes the reconciler; vitals for runs no longer in the activity snapshot never repopulate, and in-flight adoptions are dropped until the next snapshot. Separately, the reconciler is created lazily inside `onActivityFrames` but disposed in the effect — a frame arriving mid-teardown resurrects an instance whose lifetime nothing owns. Simpler shape: construct and dispose in the same effect keyed on `activityWorkspaceId`; make `onActivityFrames` a pure `ref.current?.applyFrames(frames)` consumer. PLAUSIBLE.

**m5. Provider-mismatch branch strands a run.** `acceptCandidate`: same run_id with a different harness while pending → `finish(existing, "gone")` and return, never accepting the corrected candidate — permanently abandoned if frames ever disagree on harness. In practice harness is stable per run_id, making the branch unreachable defensive code with a bad resolution; either delete it or make it re-accept the new provider. PLAUSIBLE.

**m6. `canvasStore.test.ts` is 956 LOC and S6b added two tests to it.** House rule: files over 700 are refactored before new code is added. The captured-run action tests are a natural extraction seam and the right home for the two new tests. CONFIRMED.

## Noted, not findings (doc-only)

- `candidates` map never evicts terminal entries; monotonic growth plus O(all-runs-ever) scan per snapshot on a long-lived canvas. Cheap eviction once terminal ("adopted" is re-derivable via the store; "gone" needs only a tombstone set).
- `candidateFromWire` re-validates already-typed frame items with ad hoc duck-typing while `runVitalsStore` trusts the same items and `parseActivityStreamFrame` validates only the envelope; the wire-item guard belongs at the contract seam (one validated parse, consumers get real types). Right direction for a later slice, too broad for this one.
- `adoptRun` dependency returns hardcoded `true`; the false/retry branch is dead. Either drop the boolean or make the route implementation honest.
- Cleared during verification: no unhandled rejection from the `aborted` race (`Promise.race` subscribes to all inputs); `spawnPane` cannot throw (no pane cap; deterministic paneId from runKey, collision-free); `launch_kind: "service"` flows end-to-end (TS `launchKinds` and Python contracts both carry it; browser wire type is `string | null` with no coercion); `Parameters<typeof applyFrames>[0]` matches `ActivityStreamFrame[]` exactly; snapshot-vanish → gone is the spec's own authority signal, not a bug; `createCapturedRunRef`'s new `runKey` option cannot leak into pre-existing callers (their option types don't carry it).

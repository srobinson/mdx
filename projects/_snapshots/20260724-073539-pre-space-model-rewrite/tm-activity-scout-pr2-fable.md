## HEADLINE — needs-you verdict: **ON-WIRE**. PR-2 is a pure product-plane build.

AskUserQuestion is captured, parsed, and surfaced as a distinct `needs-you` status on `ActivityWireRun` today. No capture-plane (Python, `api/**`) work is needed. The full chain, each link verified in source:

1. **Capture (already done, frozen plane untouched):** the Claude CLI transcript row lands in the Postgres session store via the transcript tailer. The assistant row's `tool_use` block with `name: "AskUserQuestion"` is present in stored rows — the repo even ships a real one in `packages/activity/fixtures/claude/claude-code-transcript.json` ("trimmed real AskUserQuestion prompt").
2. **Adapter:** `packages/activity/src/adapters/transcriptRecords.ts` → `claudeActivityRecords`: `if (block.name === "AskUserQuestion") records.add("question-asked", …)` (other tool_use blocks become `tool-use`). Codex parity in `codexActivityRecords`: `function_call` with `name === "request_user_input"` → `question-asked`. Both harnesses covered.
3. **Ports:** `packages/activity/src/ports.ts` maps record kind `"question-asked"` → machine event `"record.question_asked"`.
4. **Domain machine:** `packages/activity/src/domain/runActivityMachine.ts` — `record.question_asked` targets state `needs-you` from `starting`/`thinking`/`running-tools`/`stalled` (action `applyTurnNeedsUser`). The operator's answer arrives as that tool's `tool_result` and hands the run back (`needs-you` → `thinking`/`running-tools`). Tested: `runActivityMachine.test.ts` covers the AskUserQuestion/request_user_input answer path explicitly.
5. **Projection:** `packages/activity/src/projections/workspaceActivity.ts` → `runActivityProjection`: `status: snapshot.value` — the machine state IS the projection status, no mapping layer to lose it.
6. **Wire:** `packages/contract/src/activity/wire.ts` → `activityStatuses = ["starting","thinking","running-tools","needs-you","stalled","exited"]`; `ActivityWireRun.status: ActivityStatus`; `ActivityWorkspaceRollup.status_counts` buckets it; SSE `snapshot`/`delta` frames carry it (`activityRouter.ts`).

**One semantic nuance to surface (not a blocker):** today's `needs-you` is a **superset** of Stuart's trigger definition. `record.assistant_turn_ended` (Claude `stop_reason === "end_turn"`; Codex `task_complete` / assistant message) drives the same `needs-you` state as `record.question_asked`. So the wire status means "waiting on operator input" — explicit question OR turn finished, awaiting next prompt — and the two are **indistinguishable on today's wire**. For the minimal strip this is arguably the right product semantics (both mean "your move"). If a question-only distinction is ever wanted, it is a contract/status-vocabulary change (product plane, small), still not capture work. Recommendation: ship on the existing status per decision 3 ("just surface the statuses"); note the conflation to Stuart.

**Breakpoint distinction (brief asked):** entirely separate mechanism, no interplay. A breakpoint is a proxy-plane hold of the **next outbound request**, surfaced as `paused`/`paused_tokens` frames on the **exchange** stream (`www/packages/core/src/exchangeStreamEvents.ts`, inspector `editor/PausedHeader.tsx`). It is not a member of `activityStatuses` and never touches the activity machine. A run held at an armed breakpoint keeps its transcript-derived activity status (and would drift to `stalled` via the silence timeout if held long) — acceptable for v1, noted.

# Premise check: face lightness delta on artifact/thumbnail (base build)

**Claim under test:** `cubeFaceLightnessDeltaById` (from #160) applies on artifact and thumbnail paths as well as the workbench, so export/thumbnail does not show authored face colour faithfully today. (`edgeLightnessDelta` is already workbench-only.)

**Verdict: CONFIRMED** for the thumbnail/artifact path observed in the running app.

## Setup (driven in the live editor, not inferred)

- Worktree base build at http://localhost:5174 (this worktree).
- Single cube, Inspect → Style → Faces → **Color = White** (all faces). Authored role is uniform white (`theme` token white is `#ffffff`).
- Motion → Snapshot → **State 1** filmstrip thumbnail generated by the app.
- Default filmstrip axis is **Z** (front face, orthographic).

## Observed

### Workbench canvas
All faces authored White, yet the live cube is multi-tone: cross arms and center face read as different browns/beiges, not flat white. Orientation-driven face variation is visible by eye on the workbench.

Sampled from a full-page screenshot of that state (representative face interiors):

| Region | mean RGB (approx) |
|--------|-------------------|
| Upper arm | (102, 81, 59) |
| Lower arm | (180, 159, 136) |
| Left/right arms | (~80, 73, 67) |

### State 1 thumbnail (blob artifact, 256×256 PNG)

Pulled the filmstrip `img.cc-state-thumb` blob from the running page and counted pixels:

| Colour | Count | Role |
|--------|------:|------|
| `(204, 204, 204)` | 17424 | face fill (entire front square) |
| `(5, 5, 5)` | 47580 | background (and matches authored black `#050505`) |
| `(105, 105, 105)` / `(55, 55, 55)` | 532 | thin non-face detail |

Face fill is **flat** (one grey) but **not** authored white `#ffffff` (255,255,255).

## Match to the face-delta model

Z thumbnail shows the **front** face. `cubeFaceLightnessDeltaById.front = 0.155`.

OKLab contrast shift of linear white with magnitude 0.155, then sRGB-encoded for PNG, predicts **exactly RGB (204, 204, 204)**. Observed thumbnail face fill matches that prediction to the byte.

If the thumbnail path used flat authored colour, face fill would be `(255, 255, 255)`. It is not.

Edge pixels on the same thumbnail stay at authored black `(5, 5, 5)` with no orientation ramp, consistent with edge lightness already being workbench-only (not disproven here, and not the claim under test).

## Method notes

- Evidence is **observed** from the running app: authored via UI, screenshot of workbench, pixel histogram of the State thumbnail blob.
- WebGL `canvas.toDataURL()` returned black (no preserveDrawingBuffer); workbench samples used the agent screenshot; thumbnail samples used the app-generated blob PNG.
- No source files were modified for this check.

## Implication for the slice

Grooming that stops applying `cubeFaceLightnessDeltaById` on artifact/thumbnail (mirroring edge) is justified by this base-build behaviour: today the thumbnail does not present faithful authored face colour.

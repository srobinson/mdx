## The three RED shapes (source-reasoned at HEAD)

**1. Future-dated 304 or candidate clears a genuinely tied 403.** Denial recorded (`refreshed_at=R`, `allow_cached_use=False`, lapse minted). Affirmative arrives at the same true instant but stamped future (`2026-08-30`). `_record_acquisition` computes `ordered` with the RAW stamp → strictly newer → `_acquisition_state` returns `(None, True)`, lapse cleared, VERIFIED. Persistence then clamps via `_bounded_refreshed_at` to effective now — so the record afterwards shows a tie that the comparison never saw. Same hole in `_evaluate_candidate`'s denial-install guard and envelope-affirm gate for a 200 candidate. Clamp exists only at write, never before compare.

**2. Real 403 after wall-clock rollback is dropped, VERIFIED forever without lapse.** Record affirmed at `refreshed_at=2026-08-12` (ratchet ≥ 12th). Clock rolls back to the 11th; a genuine 403 arrives stamped `2026-08-11`. `ordered = not _is_strictly_newer_instant("…12", "…11")` → False → returns `_loaded_status` with zero mutation: no lapse, `allow_cached_use` stays True, mode VERIFIED, and the grace clock never starts. Decision 4 requires the lapse to be observed; spec §State machine requires the reason to be retained for freeze. A denial dropped for client-claimed staleness is a safety hole; a replayed denial is only an availability loss and is recoverable by the next affirmative. No existing test pins stale-denial rejection (checked `test_overlay_cache_acquisition.py` in full).

**3. Newer disabled or kill switch after 403 stays VERIFIED inside grace.** 403 first (lapse minted, `allow_cached_use=False`, reason `account_unavailable`). Strictly newer `record_acquisition(reason="disabled", allow_cached_use=False)`: `_acquisition_state` hits its sticky branch (`not record.allow_cached_use`) and returns `("account_unavailable", False)` — the kill switch is swallowed. `_entitlement_lapse_observed_at` preserves the existing lapse. `_held_status` sees the lapse marker first → grace governs → VERIFIED, reason `account_unavailable`, until the grace deadline. Spec §State machine: revocation exits VERIFIED immediately ("expiry and revocation return the tuple to `PASSTHROUGH`"; disabled artifact is a PASSTHROUGH entry). The signed-artifact kill switch via `install` already works when strictly newer and higher revision; the acquisition-observed `disabled` is the broken path, plus the tie/rollback holes from shapes 1 and 2 apply to the install path too.

## The one time boundary

Both observation-bearing entries, `OverlayAcceptedCache._record_acquisition` and `OverlayAcceptedCache._evaluate_candidate`, begin with `OverlayAcceptedCache._load_held` under the tuple lock. That post-load point is the single existing boundary where the record, the ratchet, and the incoming claim are all in hand. Establish once per incoming observation, in one shared helper on `OverlayAcceptedCache` (both entries call it; nothing else does):

- `observed_at = self._effective_now(record)` — existing ratchet reader, unchanged;
- `effective_refreshed_at = _bounded_refreshed_at(raw, observed_at)` — existing bound, hoisted from write time to establishment time.

Every subsequent comparison AND every persistence uses only these established values. This deletes the four scattered `_bounded_refreshed_at` write-site calls, the inline ratchet re-derivations in `_record_acquisition` (`_latest_instant(self._now(), …)` twice, duplicating `_effective_now`), and the raw-value comparisons. It closes shape 1 outright: a future stamp clamps to effective now, ties with the denial, and ties already resolve toward denial through `_is_strictly_newer_instant`.

For shape 2 the boundary alone is insufficient (clamp lowers, never raises). The derived rule, consistent with every existing pinned test: an affirmative must prove strict freshness — `_is_strictly_newer_instant(effective_refreshed_at, record.refreshed_at)` — but a denial (`allow_cached_use is False`) is never dropped for client-claimed staleness; it takes effect at its established instant, and its persisted `refreshed_at` is `_latest_instant(effective_refreshed_at, record.refreshed_at)` so the order water stays monotonic and a later affirmative must still beat the denial strictly. I verified this against `test_stale_affirmative_cannot_clear_a_fresher_denial`, `test_semantically_equal_utc_alias_is_not_newer`, `test_future_dated_observation_cannot_wedge_a_later_403`, `test_tied_403_cannot_be_ignored`, and the rollback suite: all keep passing under the rule.

## Denial total order

The spec states no explicit order sentence; derived from §State machine (revocation exits VERIFIED; disabled artifact enters PASSTHROUGH) plus ratified Decision 4 (grace attaches to 403 only): **disabled / kill switch > entitlement lapse (`account_unavailable`, `allow_cached_use False`) > transient (everything else)**. The directive's default order holds; the spec does not say otherwise.

Owner: `overlay_cache_record.py:_acquisition_state` — already the sticky-denial authority; the class ranking becomes a module constant beside `OVERLAY_PASSTHROUGH_REASONS` usage in `overlay_cache_record.py`. Rule: a later denial replaces the held denial only when strictly stronger; weaker or equal keeps first-writer (preserves `test_403_cannot_reopen_a_prior_kill_switch_denial` and `test_denial_is_sticky_until_an_affirmative_result`). Authority may only shrink: `allow_cached_use` stays False once False until a fresh affirmative, and lapse still mints only from good standing (`record.allow_cached_use` True — the round-3 guard stands; a 403 arriving over a transient denial must NOT mint grace, since that would widen authority).

Companion invariant for shape 3: when `_acquisition_state` escalates to the kill-switch class, `_entitlement_lapse_observed_at` must yield None (lapse cleared on escalation). Then `overlay_cache.py:_held_status` needs no second arbitration rule: no lapse + `allow_cached_use False` already renders PASSTHROUGH with the stored reason (`disabled`). Alternative — ranking reasons inside `_held_status` — creates a second precedence owner and violates the enforce-once rule; rejected.

## Duplication that must be removed by the build

- Four `_bounded_refreshed_at` call sites collapse into the one establishment point.
- `_record_acquisition`'s inline `ordered` conditional and `_evaluate_candidate`'s denial-install guard are two spellings of one ordering policy; both must consume the established observation through one predicate path.
- `_latest_instant(self._now(), record.latest_observed_at)` re-derived inline in `_record_acquisition` (twice) and `_observe_record` duplicates `_effective_now`; consolidate on `_effective_now`.
- No new comparison helper, parser, verifier, or second record writer. `_is_strictly_newer_instant`, `_latest_instant`, `require_utc_instant`, `write_atomic_json`, `exclusive_file_lock` are the owners and are sufficient.

## Reuse Map

Python: login command, home, env

- Reuse: `api/src/transport_matters/credential_source.py::_CREDENTIAL_PROFILES` + `resolve_harness_credential_source` + `harness_credential_error`. The single owner of `login_command` per harness (`claude auth login`, `codex login`, `grok login`). Both `NativeCredentialSource` and `KeychainCredentialSource` carry `login_command: str`.
- Reuse: `api/src/transport_matters/claude_fleet_auth.py::CLAUDE_FLEET_AUTH_HOME` / `CLAUDE_FLEET_BOOTSTRAP_COMMAND` (`f"CLAUDE_CONFIG_DIR={home} claude auth login"`). Selected by `credential_source.py::_claude_keychain_credential_source` on darwin. Home for the driver on macOS is `KeychainCredentialSource.owner_home`.
- Reuse: `api/src/transport_matters/launch/environment.py::HOME_DIR_ENV_BY_HARNESS` and `resolve_native_harness_home`. The only owner of `CLAUDE_CONFIG_DIR` / `CODEX_HOME` / `GROK_HOME` and native home defaults. The driver's env is `{HOME_DIR_ENV_BY_HARNESS[h]: home}`; no new mapping.
- Reuse: `api/src/transport_matters/harnesses/probes/runner.py::probe_environment(harness_id, home_dir, base_env)`. Already builds a per-harness env with the home var set and competing vars stripped for subprocess use. Candidate for producing the driver's env dict server-side.
- Reuse: `api/src/transport_matters/captured/readiness.py::_credential_check` -> `launch_readiness` -> `api/v1/launch_readiness.py::get_launch_readiness` (`GET /v1/launch-readiness`). The predicate to re-read after exit. Never mints (`require_shared=False`).
- Reuse: `api/src/transport_matters/harnesses/inventory.py::build_harness_inventory` already exports `login_command` as `authentication_command` on `GET /v1/harnesses` (`www/packages/core/src/types/harnessInventory.ts::HarnessInventoryItem.authentication_command`). The string already reaches the browser; the argv and home do not reach the gateway.
- Existing infra: `api/src/transport_matters/api/v1/run_proxy.py::RunRouteProxy` / `create_run_proxy_mount` bridges browser HTTP+WS (`/api/terminal`, `/v1/runs/{id}/terminal`) to the gateway (`_target_ws_url("/v1/terminal", ...)`). Any new gateway login WS needs one more bridge route here.
- Similar checked and rejected: `api/src/transport_matters/cli/codex_cmd.py::run_codex` passthrough (`transport-matters codex -- login`). It is a full captured launch through `prepare_launch` / `cli/runner.py::run_client_with_retry` (proxy, runtime home, session store) and its credential preflight exits before spawning. NOW.md keeps it CLI-only.
- Similar checked and rejected: `api/src/transport_matters/harnesses/probes/runner.py::_capture_probe`. `subprocess.run` with `stdin=DEVNULL`, output fully captured; no stdin path, no streaming.
- Similar checked and rejected: `api/src/transport_matters/supervisor/core.py::Supervisor.spawn` (`pty=True`). Inherits the CLI's terminal; no WS fanout. Python-side PTY hosting would duplicate the gateway's.
- None found: no Python or TS code executes a login command today. Searches: `rg "auth login|codex login|grok login|login_command" api packages www docs justfile scripts`; `rg "login" api/src/transport_matters/cli/*.py`. Login is advisory text only, so a driver is new code.

TS gateway: PTY session

- Reuse: `packages/runtime/src/ports.ts::PtyPort.spawn(PtySpawnInput{argv, env?, cwd?, cols?, rows?})` -> `PtySession{pid, write, tryWrite, resize, kill, dispose, onData, onExit}`; `NodePtyAdapter` (`packages/runtime/src/adapters/NodePtyAdapter.ts`) is the sole real implementation and buffers 64KiB pre-subscriber output. `packages/gateway/src/main.ts::createDefaultRuntimeRouterDeps` already shares one `NodePtyAdapter` between `RunManager` and `PlainTerminalSessions`; the driver takes the same instance.
- Reuse: `packages/runtime/src/service/PlainTerminalSessions.ts::PlainTerminalSessions` (`open`, `close`, `closeAll`) and `packages/runtime/src/server/plainTerminalConnection.ts::handlePlainTerminalConnection` (`WS /v1/terminal`). This is the sibling composition NOW.md 1.3 prescribes, already built: no owner, no REST, one socket owns one PTY, `session.onExit` closes attachments, `browserPtyEnvironment` shapes env. The login driver is this shape with an argv+env input and an exit frame.
- Reuse: `packages/runtime/src/service/BrowserPtyEnvironment.ts::browserPtyEnvironment(source, harness?)` (TERM, COLORTERM, strips TERM_PROGRAM/TMUX, claude alt-screen off). Wrap the driver env with it.
- Reuse: `packages/runtime/src/service/TerminalFanout.ts::TerminalFanout` (attach/append/resize/detach/closeAll, bounded queues, `retryable-overload`). Emulator (`TerminalEmulator`) only if scrollback replay is wanted; the plain terminal omits it.
- Reuse: `packages/runtime/src/server/attachmentPump.ts::pumpAttachment`, `server/socketData.ts::socketDataToBytes`, `packages/common/src/terminalContract.ts::terminalSizeFromQueryValues` / `parseTerminalResizeFrameText` / frame serializers. Stdin = binary frames, resize = `{type:"resize"}` text frame, `?cols&rows` on connect.
- Reuse: `packages/runtime/src/server/runtimeRouter.ts::RuntimeRouterDeps` (`plainTerminals?` optional field) and `registerTerminalRoutes`. Add the driver as a third optional dep and a third `register*Routes`, keeping `POST /v1/runs` and `RunManager` untouched.
- Reuse: `packages/gateway/src/main.ts::closeGatewayResources` / `installShutdownHandlers`. The new session store must join this `closeAll([...])` list or PTYs leak past process exit.
- Reuse: test doubles `packages/runtime/src/testSupport/fakePty.ts::FakePtyPort` / `FakePtySession`, `packages/gateway/src/testSupport/runtimeFixtures.ts::EchoPtyPort`, and `plainTerminalConnection.test.ts` as the test template.
- Similar checked and rejected: `RunManager.register` / `createNew` (`packages/runtime/src/service/RunManager.ts`). Carries capture lease, owner, run view, settle funnel, activity facts. Wrong-shaped for a login, as NOW.md states.
- None found: `packages/runtime/src/adapters/CaptureRpcClient.ts` exposes `prepareCapture`, `releaseCapture`, `captureHealth` only; `api/v1/capture_rpc_routes.py` serves those three. No RPC carries login argv, home, or readiness to the gateway. Searches: `rg "login|credential|readiness" packages/runtime/src packages/gateway/src`. Either the browser passes argv+env from `GET /v1/harnesses` data, or a Python endpoint hands the gateway a spawn spec (decision below).

## Quality Map

- Duplication / parallel implementation: `api/src/transport_matters/credential_broker.py::_WRITE_BACK_ERROR_MESSAGE` hardcodes `"CLAUDE_CONFIG_DIR=~/.claude-auth claude auth login"` instead of `claude_fleet_auth.py::CLAUDE_FLEET_BOOTSTRAP_COMMAND`; asserted verbatim in `test_credential_broker.py`. Cannot import it today because `claude_fleet_auth` imports `credential_broker` (would cycle). The one real drift risk.
- Duplication / parallel implementation: `api/src/transport_matters/cli/home_constants.py::_CLAUDE_CONFIG_ENV` / `_CODEX_HOME_ENV` re-declare keys already in `launch/environment.py::HOME_DIR_ENV_BY_HARNESS`, which the same module imports.
- Duplication / parallel implementation: the pair `resolve_harness_credential_source` + `harness_credential_error(require_shared=False)` is evaluated in three places: `cli/diagnose.py::_report_credential_readiness`, `captured/readiness.py::_credential_check`, `harnesses/inventory.py::build_harness_inventory`. Only doctor adds `shared_access_credential_error`, so doctor and HTTP readiness can disagree on a stale macOS shared credential.
- Duplication / parallel implementation: test fixtures re-spell the strings: `www/packages/canvas/src/firstrun/harnessInventory.testSupport.ts`, `FirstRunScreen.test.tsx`, `api/.../harnesses/test_inventory.py`. Fixture data, low risk.
- Boundary / design issue: `login_command` is a shell string (`CLAUDE_CONFIG_DIR=... claude auth login`), not argv + env. `PtyPort.spawn` takes `argv` and `env`. The driver needs a structured spec (`argv: [...]`, `env: {CLAUDE_CONFIG_DIR: ...}`, `cwd`) and the display string derived from it, or the shell string must be parsed. Deriving is the correct direction; parsing a display string is wrong-shaped.
- Boundary / design issue: `captured/readiness.py::LaunchReadinessCheck.remediation` is `None` for every credential check; `infrastructure_guidance.py` carries no credential remediation. `templateRows.ts::launchBlockedReason` never reads `remediation`. The login command reaches the browser only through the `detail` prose and through the separate inventory endpoint.
- Boundary / design issue: `captured/` imports `cli/` (`captured/run.py`, `models.py`, `invocations.py`, `claude.py` from `cli/runner`, `cli/launch_profile`, `cli/launch_runtime`; `baseline_capture.py` from `cli/home_seed`; `configured_launch_model.py` from `cli/home_constants`), several as deferred function-body imports. The inversion NOW.md warns about. Not on the login path if the driver stays out of `cli/`.
- Boundary / design issue: browser WS reaches the gateway only through the Python bridge (`api/v1/run_proxy.py::RunRouteProxy`, `/api/terminal` -> `/v1/terminal`). A login WS is a fourth hop: browser -> FastAPI bridge -> Fastify -> PTY. The bridge file is 628 lines.
- Dead code / obsolete path: none in the credential modules. `credential_source.py::claude_keychain_credential_source` is test-only by design (documented). `docs/overlays/tm-overlay-worksheet-claude.md` tells the agent to ask the user to type `! <command>` for logins, contradicting 1.3's "never asked to type one"; overlay prompt text, not TM behaviour.
- Sizing near the 700 cap (new code must not land here without refactor): `credential_broker.py` 668, `api/v1/capture_rpc_routes.py` 670, `harnesses/inventory.py` 611, `api/v1/run_proxy.py` 628, `packages/runtime/src/service/RunManager.ts` 685, `www/packages/canvas/src/firstrun/FirstRunScreen.tsx` 623. Tests over 600: `test_credential_broker.py` 695, `cli/test_diagnose.py` 659, `cli/test_home_seed_credentials.py` 619, `runtimeRouter.test.ts` 668, `CapturedRunPane.test.tsx` 657, `commandRows.test.ts` 662.
- Gate coverage: `www/packages/core` and `www/packages/canvas` have no `test` script; their tests run through `www/packages/shell/vite.config.ts` projects (`../core`, `../canvas` globs) via `just test-js`. Correct, but a targeted `pnpm --filter @tm/canvas test` does not exist.
- Grooming recommendation: refactor during the slice for `FirstRunScreen.tsx` (extract `HarnessCardItem` before adding a sign-in action) and `run_proxy.py` (extract the WS bridge helpers before a third WS route). Refactor first for `_WRITE_BACK_ERROR_MESSAGE` by moving `CLAUDE_FLEET_AUTH_HOME` / `CLAUDE_FLEET_BOOTSTRAP_COMMAND` below `credential_broker` (or into `launch/environment.py`) so both import one constant. Defer the triple readiness evaluation and `home_constants` duplicates with reason: not on the driver's path; file as follow-up.

## Plan

- Decision needed: how does the gateway learn the spawn spec? (a) Python exposes `GET /v1/harnesses/{id}/login-spec` returning `{argv, env, cwd, display}` derived from `resolve_harness_credential_source` + `HOME_DIR_ENV_BY_HARNESS`, and the browser passes it on the WS query/first frame; (b) a fourth `CapturePort` RPC so the gateway asks Python itself. (a) keeps the gateway ignorant of harness facts, matching how it works today; (b) adds an RPC method to a 670-line route file. Recommendation: (a).
- Decision needed: surface. A canvas pane (registry `PaneContentRef` kind, lazy xterm, non-blocking) versus a new Ark `Dialog` (focus trap, new CSS, blocks the canvas). A pane reuses `TerminalPane.tsx` shape with zero new primitives; the fallback URL is visible in the PTY output either way.
- Decision needed: `login_command` shape. Keep the shell string on `CredentialSource` for prose and add a structured `LoginSpec` beside it, or replace the string with the spec and render the string from it. Replacing removes the duplicate.
- Decision needed: grok. `_CREDENTIAL_PROFILES` already says `grok login`; confirm the binary honours it before the driver claims three harnesses.
- Proposed steps bound to the reuse map:
  1. Python: add `LoginSpec(argv, env, cwd, display)` derived in `credential_source.py` from `_CREDENTIAL_PROFILES` + `HOME_DIR_ENV_BY_HARNESS` (`owner_home` on darwin claude); route in `api/v1/` alongside `launch_readiness.py`; export on inventory as the source of `authentication_command`. Groom `_WRITE_BACK_ERROR_MESSAGE` to import the shared constant. Tests colocated: `test_credential_source.py` (new; none exists).
  2. Gateway: `packages/runtime/src/service/LoginSessions.ts` modelled on `PlainTerminalSessions` (`open({argv, env, cwd, cols, rows})`, `browserPtyEnvironment`, `TerminalFanout`, `onExit` -> close with exit code in the close reason); `server/loginTerminalConnection.ts` modelled on `plainTerminalConnection.ts`; third optional field on `RuntimeRouterDeps`; `WS /v1/login`; add to `closeGatewayResources`.   3. Bridge: one `@router.websocket` in `run_proxy.py` forwarding `/api/login` -> `/v1/login`, after extracting the bridge helpers so the file stays under 700. Test beside `test_terminal_bridge.py`.

## Quality Map

- Boundary / design issue: the record/fact → `RunActivityEvent` translator consumes `ports.ts` DTOs (`ActivityRecord`, `RunLifecycleFact`) and produces `domain` events. It **must live in `service/`, not `domain/`**: `ports.ts` already imports `./domain`, so a `domain → ports` edge is an import cycle and breaks the pure/IO layering (`docs/ARCHITECTURE.md` Effect boundary: `domain/` stays pure and self-contained). Fact.
- Boundary / design issue: `runActivityMachine.ts` `RunActivityContext` has **no `since_ts`** field (the ts at which the current status began). Spec §5.3 requires `since_ts`. The projection must capture the transitioning event's `.ts` (events carry `ts`), or context must gain the field. Fact.
- Boundary / design issue: overview and `context_tokens` are **unmodeled**. `ActivityRecord` (`ports.ts`) carries no prompt / last-agent-message text, so `initial_prompt`/`last_message` (spec §3, §5.3) cannot be projected from current inputs; and the machine *sums* usage (`context.usage`) but does not retain the last window, so `context_tokens` (a current-window value per §3, not a monotonic sum) is not derivable from `context.usage`. Both belong to the §5.3 read surface = **slice 3**, not slice 2's projection. Scoping decision, below.
- Boundary / design issue: `RECORDS_BY_RUN_SQL` (`postgresRecords.ts`) orders by `(session_id, seq)`, but the machine dedupes on a **single `record` cursor**. If one run spans multiple sessions and `event.seq` resets per session, the second session's low-seq records would be dropped as stale (`seq <= cursor`). Fact to verify (decision below).
- Dead code / obsolete path: `ports.ts` `Clock` interface is defined and re-exported from `src/index.ts` but has **zero consumers** (`grep -rn "Clock"` → only its declaration and the barrel re-export). It is a forward commitment, not dead; slice 2 may wire it for `since_ts`/doctor wall-clock, or leave it. Note: xstate's actor clock (delays) is separate from `ports.Clock` (`now(): Date`); do not conflate them.
- Duplication / parallel implementation: none present. Temptations to guard against: (a) re-deriving a kind→type switch instead of reusing `activityRecordKindEventTypes`; (b) re-implementing seq dedupe instead of delegating to `isNewEvent`; (c) writing an in-package coercion instead of using `@tm/common` primitives.
- Grooming recommendation: refactor during the slice. No pre-slice refactor is owed. The only edit to an existing file is a new enumeration query on `PostgresActivityReader`; everything else is additive under `service/` and `projections/`. Keep the translator in `service/` to hold the layering line.

## Plan

- Decision needed (projection scope): does slice 2's projection carry only `status` + `since_ts` + `total_usage` + lifecycle fields (`harness`, `launch_kind`, `exit_reason`), deferring `initial_prompt`/`last_message`/`context_tokens` (spec §5.3) to slice 3 with the HTTP read surface? Current inputs (`ActivityRecord`, machine `context`) support the former but not the latter without new record fields.
- Decision needed (restart enumeration): what defines a "replayable" run for restart — all runs in a workspace, or runs in `run_lifecycle_event` lacking a `run-exited` row? And is the replay set workspace-scoped or global at boot? Drives the new reader query shape.
- Decision needed (multi-session cursor): confirm whether a single run can span multiple `session_id`s with per-session `seq`, which would break the single `record` cursor. If yes, the record stream needs a composite/global ordering; if no (run == one session for replay purposes), document the assumption.
- Decision needed (clock injection): production actors use xstate's real scheduler; tests inject `SimulatedClock`. Confirm the service exposes a clock-injection seam (createActor `clock` option) and whether `ports.Clock` is wired for `since_ts` or left unused this slice.

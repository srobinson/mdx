## Verdict

I sign off conditional on: (1) resolving the cascade-stop server-expressibility gap, (2) adding the tree edge / cycle-guard / set-parent work as an explicit slice, (3) not conflating Alembic revisions with browser cache "storage version". The two drafted docs are sound and their reuse map is faithful, but the four LOCKED DECISIONS (Canvas-as-tree, subtree delete, `parent_canvas_id` edge, cascade-stop via pane-close path) are net-new *beyond* what either doc plans. Neither doc mentions `parent_canvas_id`, a tree, or subtree delete; the scout treats Canvas delete as a flat single-row concern (scout PR3). The locked decisions are buildable but not yet reflected in the slice plan, and one of them (cascade-stop) is not expressible against today's runtime.

## PRIMARY — delete semantics

### 1. Subtree cascade + `parent_canvas_id` (cycle / depth / orphan)

- **`parent_canvas_id` does not exist.** `space.models::Canvas` has `canvas_id, space_id, owner, name, default_worktree_id, layout, layout_version, archived, created_at, updated_at` — no parent edge. The `canvas` table in migration `0006_spaces_foundation` has no parent column. The locked "TREE / SUBTREE DELETE" decision therefore requires a new nullable self-referential column + migration + model field + every read/write path that projects Canvas. This is real net-new scope absent from both docs.
- **Orphan prevention is partly free, partly not.** A self-FK `parent_canvas_id REFERENCES canvas(canvas_id) ON DELETE CASCADE` makes Postgres delete descendant canvas *rows* transactionally — orphan canvas rows are structurally impossible. But panes and runs are **not** in Postgres (panes: browser localStorage via `canvasCacheStorage.createCanvasCacheStorage`; runs: in-memory `RunManager.runs` Map in the node process). A DB cascade removes rows and does nothing to panes or runs. The subtree "delete node + descendant canvases + their panes/runs" is a **distributed** operation, not one transaction.
- **Cycle / self-parent guard is mandatory and unplanned.** A Postgres self-FK does not prevent `A.parent = A` or an `A→B→A` cycle. The guard must live at write time in the service, on whatever operation *sets* `parent_canvas_id`. There is no such write operation anywhere in the drafted plan (the scout's Canvas update covers name + default worktree + layout only). A cycle is not merely a data smell: the application-layer subtree walk needed for run-stop and cache-clear (a `WITH RECURSIVE` over `canvas`) will infinite-loop on a cycle, and `ON DELETE CASCADE` on a cyclic graph is undefined intent. Cycle-safety is required in both the write guard and the walk.
- **Depth is unbounded.** Arbitrary nesting is fine for `ON DELETE CASCADE` and a recursive CTE, but the walk must carry a visited-set / depth cap as defense against the cycle case above.
- **Flat case = depth-0** is coherent: `parent_canvas_id` null default means every existing canvas is a root; today's flat behavior is the depth-0 special case, no behavior change for current data.

### 2. Cascade-stop runs — TOP BLOCKING FINDING

- **The named path does not exist by that verb.** There is no `DELETE /runs/{id}`. The real stop path is `POST /v1/runs/{runId}/terminate` (browser `transport.terminateRun`) → node `POST /runs/:runId/terminate` → `RunManager.terminate(runId, owner, reason)`. The per-run terminate primitive is real and reusable; the verb in the locked decision is wrong but harmless.
- **Runs carry no canvas identity anywhere.** Verified across `packages/runtime/src`: a run's create input and `RuntimeRunView` (`runManagerTypes.ts`, `domain/runtimeRun`) carry `workspaceId, spaceId, worktreeId, launchKind` — **no `canvasId`**. `RunManager.list` filters by `owner, state, spaceId, worktreeId` only. **The server cannot answer "which runs belong to canvas X", so a server-side bulk subtree cascade-stop is not expressible today.** The pane→run association lives only in the browser (`capturedRunStore`, canvas cache). Consequence: cascade-stop is inherently client-driven and can only reach canvases the *current* browser has hydrated — descendant canvases never opened this session, or runs owned by another client, are unreachable. This is the crux the brief asks about, and the answer is **client-only today**.
- **Decision required before the subtree-delete slice:** either (a) add `canvasId` to the run create contract + `RuntimeRunView` + a `list` filter, so the server can enumerate and cascade-stop by canvas subtree; or (b) accept an explicitly best-effort client-only cascade that cannot guarantee stopping runs in un-hydrated / foreign-client canvases. Option (a) is the only one that makes the locked "delete descendant panes/runs" semantics truthful.
- **Race — in-flight create into a canvas being deleted:** `RunManager` tracks `pendingCreates` (a Map) separately from `runs`, and `list()` returns `[...this.runs.values()]` only — pending creates are invisible to the inventory. A create that has passed launch availability but not yet registered will be missed by any cascade that reads `list()`. The gate/inventory port (scout missing-primitive #9) must consult **both** `runs` and `pendingCreates`, keyed by the target. The data exists; it is just not surfaced — so this is buildable, not a redesign.
- **Partial failure is intrinsic, not an edge.** Row deletion is transactional in PG; run termination is N best-effort cross-process HTTP calls, some of which can fail (a detached PTY may refuse to die). The design must NOT promise transactional stop-all. It should promise: transactional row deletion + best-effort run stop + a structured multi-phase receipt (scout's fixed non-negotiable is correct). Decide explicitly whether a run that won't stop **blocks** the subtree delete or is **reported as orphaned** — do not leave it implicit.

### 3. Worktree-dirty

- **No production git-dirty check exists, but a real precedent does** and neither doc cites it: `harnesses/certification_minting` runs `git status --porcelain --untracked-files=all` and rejects on "worktree is not clean". `space.detection.detect_space` only observes via `git worktree list --porcelain`. The safe-delete preflight should promote the certification dirty-check into the shared Git worktree port (scout missing-primitive #6/#8), not re-invent it. Reuse-map gap.
- **stub-identity blind spot.** `RunManager` falls back to `DEFAULT_WORKTREE_ID = "stub-worktree"` (and `DEFAULT_SPACE_ID = "stub-space"`) when a launch has no resolved worktree. A run actually writing into the worktree being deleted, if it launched unresolved, will **not** match `list({worktreeId})` and is invisible to the run-guard. The dirty/run preflight must reject unresolved/stub identities (scout finding #16) or it has a hole.
- **TOCTOU on the tree.** In-flight runs keep writing to the working tree. The dirty check is a point-in-time snapshot; a run can dirty the tree the instant after the check passes. The atomic launch gate/lease must be acquired **before** the dirty check and run-inventory read, and must exclude the worktree from new launches for the duration, or the "blocks on dirty" guarantee is racy.

### 4. `parent_canvas_id` migration

- **Data-loss-safe and trivial.** New nullable column, default null; every existing row backfills to null = flat = current behavior. No destructive backfill.
- **Do not conflate two "storage versions".** The Python persistence layer versions via Alembic revisions (`api/migrations/versions/0006`…`0029`); there is no numeric "storage version" to bump there — a new revision *is* the mechanism. The "storage version bump" instinct in the brief maps to the **browser** cache (`canvasCacheStorage` / localStorage), which is a **separate** authority (scout authority-finding #1: durable UUID vs synthetic local IDs). If the tree edge changes what the browser persists per canvas, that is where a cache-version bump and the persist-OLD-snapshot-then-rehydrate test belong — not in Alembic. Keep the two planes distinct or the migration slice will test the wrong thing.

## SECONDARY

- **Reuse-map fidelity: faithful.** Verified real: `space.models::Canvas/Worktree`, `SpaceStore.{list_canvases,create_canvas,update_canvas,get_worktree,list_worktrees,resolve_worktree,_upsert_worktree,_claim_git_space,_lookup_space_for_detection}`, `api/v1/launch_resolution.resolve_run_worktree`, control-plane MCP (`create_control_plane_mcp`, `ControlPlaneMcpAuthApp`, `_McpControlPlaneAdapter` — confirmed via imports), `RunManager.{list,terminate}`. No MCP space/canvas/worktree tools exist (gap confirmed). Scout finding #6 confirmed: `update_canvas` COALESCEs `default_worktree_id`, so explicit-null cannot clear it. Two map corrections: (a) `canvas_default_worktree_fk` is already `ON DELETE SET NULL`, so worktree-delete → canvas-default cleanup is partly free at the DB layer; the docs overstate the manual cross-ref work for that specific edge. (b) `session.space_id`/`worktree_id` indexes have no FK — dangling-session-ref risk on hard delete is real (scout #14 correct).
- **Twin-client is genuinely one path and contract-aligned.** `SpaceCrudService` is net-new (no existing symbol), both adapters (REST via `space_routes` extraction, MCP via `_McpControlPlaneAdapter` + focused registration) are real seams. Sound. Direct-`SpaceStore`-from-MCP exclusion is enforceable by the private-import boundary test already in the repo.
- **Slice buildability.** PR1–PR5 as drafted are buildable and correctly ordered (authority before mutation, policy-gate before destructive). The gap is that the locked tree/subtree decisions are **not represented** in any slice: the tree column + backfill, the set-parent write op with cycle guard, the recursive subtree walk, and (if chosen) `canvasId`-on-runs must be inserted — most naturally as a slice before PR3, with PR3 becoming "subtree delete" rather than "flat canvas delete".
- **Forecloses ad-hoc multi-launch / batch?** No. Adding `canvasId` to the run contract would *help* batch launch (runs become canvas-addressable). Nothing here forecloses the layers above.

## Top blocking finding

Cascade-stop of runs is not expressible server-side: no canvas→run edge exists (`RuntimeRunView` and `RunManager.list` have no `canvasId`; pane→run lives only in the browser). Either add `canvasId` to the run create contract + view + list filter, or accept an explicitly best-effort client-only cascade that cannot reach un-hydrated or foreign-client runs. Decide before building the subtree-delete slice.

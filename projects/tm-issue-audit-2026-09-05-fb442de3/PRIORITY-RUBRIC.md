# Priority and reconciliation rubric

The deliverable is an execution backlog, not a relabeling exercise. Separate urgent defects, core product progression, and optional investments. Existing labels are inputs, not verdicts.

Rank by concrete user harm or blocked core promise first, then breadth and frequency, then work unlocked, then expected cost and implementation risk. Prefer a small independently verifiable correction when it yields clear immediate value. Do not infer incidence from a single reproduction or invent numeric ROI. Label effort as an estimate S/M/L. Preserve dependencies even when a dependent outcome has higher intrinsic value.

The central product promise is automatic support for new harness/model releases plus truthful inspection and safe overlay application. Integrity of provider-bound transformations and truthful support status outrank convenience. Established provider/account refusal is distinct from compatibility uncertainty; clarify provenance and policy instead of silently choosing one.

Represent each open issue exactly once in the issue ledger. Umbrellas link to implementation packages and contribute no duplicate effort. A merge recommendation names the surviving issue and preserves unique acceptance criteria. Shared modules do not prove duplicate work. Split oversized issues at independently deliverable outcomes, not arbitrary filenames. Identify current implementation, open PR work and unverified boundaries separately.

Final deliverables: priority-ordered work packages; complete 43-issue disposition ledger; explicit dependencies; unresolved owner decisions; closure/merge/rewrite recommendations supported by current evidence; and concise first-work recommendation. No GitHub mutation is authorized by this audit request.

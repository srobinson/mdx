# Cubicell Audit — App Composition and UI Architecture (Agent 4 of 4)

Baseline: main @ 71098b4, clean checkout. Slice: `src/app/`, `src/state/`, `src/panels/`, `src/studios/`, `src/studio/`, `src/controls/`, `src/editor/`, `src/thumbnail/`, `src/config/`, ARCHITECTURE.md. Read only; navigation via fmm.

## Verdict

**RESTRUCTURE, scoped narrowly to the app shell; everything else in the slice is GROOM. Emphatically not REBUILD.**

Answering the mandated headline question directly: **the app composition survives the locked three-space studio and recursion.** The three-space target (Browser, Editor, Animation Studio, tabs, rehydrate-on-switch) requires moving boundaries in `src/app/` and lifting the one-shot boot into a router, which is "keep the model, move the boundaries" for that one directory. It does not require touching the store model, the studio substrate, the panels, or the command layer, because the locked tab model ("active tab is live; switching rehydrates") describes a single-live-document runtime, and that is exactly what the current store already is. Recursion costs `src/state/` a mechanical tax, not a reshape, because state treats cube identity as opaque membership. Detail in "Addendum findings" below.

Three strongest pieces of evidence for the overall judgment:

1. **The composition layer is provably testable at the top.** `tests/editorStudioTestSupport.tsx` (`EditorStudioTestRoot`) mounts the real `Studio` from `src/studios/editor/EditorStudio.tsx` with the real `SharedRendererModule`, mocking only the WebGL leaf (`CubeScene`). It is exercised by `tests/appPlaybackBoundary.test.tsx` and the `playbackFrame` and `demandRendering` browser drivers. The most serious possible finding in this slice, structural untestability at the seams, is false.
2. **Module health is excellent by direct measurement.** No file in the slice exceeds 700 lines (max: `src/state/projectDurability.ts` at 686). A whole-repo duplication scan returned exactly two clusters, both intentional pairs (inverse projection math in `src/pose/projectionMatch.ts`, a command pair in `src/editor/commands.ts`). Every cross-chunk boundary import I checked (`PieceStateStrip` into `src/studios/editor/`, `src/panels/BottomDock.tsx`) is type-only.
3. **Every defect found has an incremental fix whose target shape already exists in this codebase.** The render-refreshed ref problem is fixed by the pull-based port shape already used three files away (`capturePort` in `useRecordingCapability`, `panelDragPort`, `horizontalScrollPanPort`). The budget ownership map is fixed by file moves. Nothing forecloses anything.

## Addendum findings (three-space studio, recursion, assetPoster, command bus)

**A1 — The locked three-space studio: absorbed with a bounded app-shell reshape; no wall.** Correcting one premise first: `src/app/App.tsx` does not exist on main (only in ARCHITECTURE.md, which is stale, see G2); the composition shell is `src/studios/editor/EditorStudio.tsx`. The incremental path, concretely:

1. *In-app space navigation.* Today `src/main.tsx` calls `beginRouteLoad(window.location.pathname)` once at module scope; there is no in-app switch. But the machinery underneath was built for repeated opens: `AppBootstrap` takes the load session as a prop, `StudioHost` keys on `session.id`, and `createStudioGenerationSource().open(key)` reuses the current owner for a same-key open and disposes the previous generation (reverse-order disposers, `isCurrent` guards) on a new one. The reshape is lifting `beginStudioLoad` into a small router state that re-renders `AppBootstrap` — the boot shell is 22 lines. The one-shot `startupIndicator` lifecycle generalizes to per-space; minor.
2. *New spaces.* Browser and Animation Studio are additive catalog entries: `catalogData` + loader + budget delivery block, with isolation already enforced (`CROSS_STUDIO_IMPORT`, per-studio delivery roots). `DesignSystemStudio` at 8 LOC is the proof of shell cost. The blocker to building them cleanly is T2: a second real studio today would raid editor-flavored modules out of `src/app/`. Execute T2 first (that is the reshape).
3. *Tabs, auto-save on switch, rehydrate.* The store is already a single-live-document runtime with every verb the locked lifecycle needs: `hydrationStatus`, checkpoint and enqueue paths through the durability coordinator, `restore-structure-asset`/`restore-animation-asset` operations, `userProjectState.activeAssetId`, and the attached/detached working scene distinction that maps exactly onto "an editor may be empty and unsaved, but an asset is never stateless." Tab switch = existing checkpoint + existing restore operation + existing session repair. Open-tab lists per space are session state extending `userProjectState` (the `panelLayout` precedent), matching the locked "persisted locally per user and Project."
4. *One live canvas.* `SharedRendererModule` is already a separate delivery root designed to be shared across studios; the budget treats it as its own delivery with anchored-by-design ownership.
5. *The residual cost that is real:* project-level switching (not tab switching) needs a new store instance, and `useCubicellStore` currently `Object.assign`s the module-singleton `browserRuntime.store` as a provider fallback, so the singleton is the de facto path. Making `CubicellStoreProvider` mandatory is part of the reshape. Also noted as directed: `design-system` is a registered studio the product docs never mention; it is a dev surface and should be named as such somewhere.

Where would the incremental path break? I could not make it break. Every step lands on machinery that already exists and was visibly built in anticipation. **Classification: TAX today (the reshape must happen before the second space lands), no WALL.**

**A2 — Recursion's identity cost to `src/state/`: mechanical TAX, with one cross-slice landmine that is not mine.** Verified by grep: nothing in `src/state/` parses `cubeId` internals (no split/slice/parse/startsWith over ids). `repairEditorSessionReferences` reconciles by membership in a `Set` of live ids; `historyDiff` encodes RFC6902 ops over workbench JSON (shape-agnostic, survives nesting, diffs deepen); selection types arrive from domain and are treated opaquely. If cube identity becomes a path-qualified opaque string (instance path + local id), session repair, selection assembly, and history survive unchanged. The concentrated costs: `reduceAuthoredOperationState`'s `hasUniqueCubeIdentitiesAndCoordinates` (global uniqueness becomes per-grid-instance uniqueness), the `cellsById`/`cellsByCoordinate` maps in `sceneOperationReferencesValid` (they assume one flat cell list; they survive if the working scene remains a flattened projection of instances), and reducer validation per family. That is wide but shallow. **The landmine is upstream in the domain slice:** state's entire repair contract rests on "stable cube ids reconcile by membership alone" (`sessionReferences.ts` doc comment), while ARCHITECTURE.md records that lattice operations "shift cell coordinates and ids." Coordinate-coupled id minting is the one thing recursion actually breaks; if ids become path-qualified and stable, my slice pays a mechanical tax; if ids keep deriving from coordinates, membership repair degrades under reuse. Flagging for the domain auditor.

**A3 — `assetPoster.ts` forward declarations: healthy anticipation, keep.** 31 LOC, two exports (`resolveAssetPosterState`, `resolveAssetThumbnailSet`), no production caller, covered by `tests/thumbnailAssetPoster.test.ts`, correctly homed in `src/thumbnail/`, and it now has a named consumer (the Browser space). This is what good forward declaration looks like: small, tested, in the right home, with an arriving customer. The contrast case in this slice is `src/studio/` (G1): 412 LOC of maintained, unmounted feature. Judge speculative weight per instance by size and by whether a consumer is on the roadmap; here the answer is keep.

**A4 — The command bus is the primary path but not a chokepoint; making it one is enrollment, not reshape.** Counted on main: the bus (`useEditorCommandDispatch`/`runEditorCommand`) is dispatched from **~20 files**; meanwhile **~37 direct store-action call sites across 18 UI files** bypass it (grep inventory, excluding `useSynchronousEditorCommands`, which is the bus's own executor). Broken down: (a) `src/app/useSceneOperations.ts` holds ~5 direct `dispatchAuthoredEdit` sites — neighbor placement, build visibility, grid composer rebuild — exactly LLMDRIVES' named gaps; (b) the motion panels hold direct edit and lifecycle sites (`selectActiveState` ×2, `beginHistoryBatch`/`endHistoryBatch` ×2 each); (c) an entire *modality* bypasses the bus: continuous authored scrubs run through `useAuthoredScrubGesture` → `authoredGesture` begin/preview/commit against the history coordinator, used by StructureSection, AssemblyControls, ControlBindingField, MotionInspector, and the parked CameraTrackControls; (d) ~16 distinct session-UI actions (tabs, layout, hover, axis hints) plus `patchPreferences` ×4, which arguably belong outside a *document* command bus; (e) the transport clock advances via `TransportFrameDriver` outside the bus (sibling slice, named in ARCHITECTURE.md as deliberate). So: **one primary path plus three structural side doors** (discrete direct edits, the scrub modality, session/preference writes). The convergence LLMDRIVES wants is additive because the synchronous lane is registry-based (`registerCommand` descriptors with `canRun`/`run` over injected ports): enrolling `useSceneOperations`' flows means writing descriptors around store actions that already exist. The genuinely hard part is the scrub modality — the bus has camera holds but no concept for continuous authored transactions, and `authoredGesture` is its own transaction object; an LLM control plane that wants to drive scrubs needs the bus to grow a gesture lane or to address the gesture port directly. **Classification: TAX (enrollment work plus one missing bus concept), no WALL.**

## Walls

**None found.** I looked hardest at the two candidates:

- *The React-to-imperative ref boundary* (question 1). A wall requires that the incremental path breaks. The incremental path is: replace each render-refreshed ref with a pull at call time against a stable source, the shape the same file already uses for framing and selection (`framing: () => readStoreFramingInputs(store.getState())` in `useEditorCommands`). It does not break; see Taxes.
- *Composition-layer testability* (question 6). A wall would mean the seams cannot be mounted. `EditorStudioTestRoot` mounts them. The injection points are real: renderer arrives as a module prop through `StudioViewProps` (`src/studios/contract.ts`), the camera authority is a parameter of `useEditorCommands`, the store is context-injectable (`CubicellStoreProvider`), lifecycle is a plain object. The incidents that motivated this question (tests passing through bespoke harnesses while production wiring was deleted) are a policy failure, not a structural one: nothing *requires* a surface test to mount the studio, and the harness path (`selectorPanelTestHarness.tsx`, `structureSectionTestHarness.tsx`, `motionTimelinePanKeyboardFixture.tsx`) is the path of least resistance. The fix is a gate (integrator-level tests must use `EditorStudioTestRoot`, per the existing fixture-certifies-fixture lesson), not a rebuild.

## Taxes

**T1 — Render-refreshed mutable refs into the interaction core.** `src/app/useEditorCommands.ts` feeds the persistent core through `projectionRef` and `syncPortRef`, both assigned during render. Judging the whole pattern as directed: it is *structurally weak, and both existing instances are already unnecessary.* The core proves this itself: its `framing` and `selection` ports pull `store.getState()` at call time with no ref. `projectionRef` duplicates a value derivable from the same store read. `syncPortRef` exists only because `useSynchronousEditorCommands` collects ~21 Zustand actions through React hooks; those action references are stable on the store, and the one genuinely dynamic input (`capturePort`) is itself already a stable pull-based port (`useRecordingCapability` builds it once and delegates to `capability.getSnapshot()` at call time). A plain `createSynchronousExecutor(store, capturePort)` eliminates the ref and the hook-ordering chicken-and-egg that forced it. The third-ref SHOEHORN was the pattern reaching its natural failure: freshness delegated to a layout effect in a component the owner does not control. **Cost:** every new core input proposed as a ref triggers the same adversarial review cycle, and second consumers cannot reach closure-sealed reads without editing `useEditorCommands`. **Named replacement shape:** stable pull-based ports (read `store.getState()` or a capability snapshot at call time) for values, subscribable registration ports (`panelDragPort`, `horizontalScrollPanPort` in `src/app/`) for DOM/consumer-registered inputs. Roughly an afternoon to delete both refs; after that, reject refs at review.

**T2 — `src/app/` is a mislabeled grab-bag.** Only `AppBootstrap` and `startupIndicator`/`startupIndicatorMarkup` are true bootstrap (confirmed from `src/main.tsx`). The other ~17 modules (`StudioShell`, `DockablePanel`, `FloatingKeypad`, `PersistenceStatus`, `panelResize`, `SelectionFocusDriver`, `SelectorTabDriver`, `stageInteraction`, `useEditorCommands`, `useSceneOperations`, the ports, `useAuthoredScrubGesture`) are consumed exclusively by `src/studios/editor/`, `src/capabilities/`, and `src/panels/`. **Cost:** the name misleads every placement decision (`useAuthoredScrubGesture`, an authoring gesture hook, landed here and is consumed by panels and the parked studio), and a second product studio would either import editor assumptions from "app" or duplicate them. The studio concept is sound (see Fine); this directory is the one thing undermining it. Incremental fix: move editor-only modules under `src/studios/editor/` or a named shared studio-shell home; `src/app/` keeps bootstrap only.

**T3 — The delivery budget hand-maintains an ownership map that file placement contradicts.** Answering question 5 directly: budget-enforced splitting is **not** distorting placement; I found no module placed to satisfy a budget. The distortion runs the other way: because motion panels live in `src/panels/motion/`, thumbnails in `src/thumbnail/`, and recording in `src/export/`, `budgets/initial-delivery.json` must encode ownership by enumeration (`capabilitySourceRules` with prefixes, plus an `exact` rule for `src/panels/BottomDock.tsx`), and `vite.config.ts` special-cases `src/panels/editorCommandContext.ts` and two scene modules by name in the initial-shared matcher. **Cost:** two sources of truth for ownership; each new capability-adjacent file needs a matching rule edit, and the rules rot silently as files move. Incremental fix: relocate capability-owned code under its capability (e.g. `src/capabilities/motion/panels/`), after which most `capabilitySourceRules` collapse to the `src/capabilities/` prefix that already exists as the fallback.

**T4 — Session-state consistency is enforced by three separately named seams with different blind spots.** `editorWithReconciledSelection` (`src/state/cubicellHistory.ts`), `reconcileAssemblyAgainstScene` (`src/state/selectionAssembly.ts`), and `repairEditorSessionReferences` (`src/state/sessionReferences.ts`) all answer "make session state consistent with the new document," at different granularities. Repair itself is narrow and honestly documented (membership-only pruning; dead IDs, never content changes), which is why this is not the catch-all the audit brief feared. **Cost:** each new session reference must be enrolled in the right seam by memory, and a miss fails silently; this session's surprise (content change, surviving ID, stale session meaning) is exactly the gap between seams. Incremental fix: one named session-projection seam that owns the whole contract, with the three current functions as its internals, plus an explicit statement of what content-level reconciliation is *not* provided.

## Grooming

**G1 — `src/studio/` is a parked feature wearing a boundary's name.** `CameraTrackControls` + `cameraCapture` (412 LOC) have zero production consumers; the only importer is `tests/studioCameraControls.test.tsx`. Git shows this is deliberate: PR #86 (F1 Piece Motion cutover, 2026-07-17) unmounted it from panels and moved it here as parked authored-camera-tracks work, and it still receives maintenance (#135 touched it). Per the repo's own lesson, this is a parked capability, not dead code, but it currently costs maintenance on every scrub-gesture change while colliding with `src/studios/` in every human and tool conversation. Decide: name it as parked (`src/parked/camera-track/` or a doc marker) or delete with a revival tag.

**G2 — ARCHITECTURE.md drift.** Items 43 and 45 describe `src/app/App.tsx` as the composition shell and reference `src/app/useSelectionFocusCommands.ts`; neither file exists. The composition shell is `src/studios/editor/EditorStudio.tsx`. The doc also does not mention `src/studios/` at the "Current Source Boundaries" level where it lists everything else. For a document feeding a rebuild decision, this is the first thing to fix.

**G3 — Dead ternary in `createAuthoredDispatcher`.** The `origin === "local"` conditional building `update` in `src/state/actions/authoredDispatcher.ts` has byte-identical arms.

**G4 — `editorCommandContext.ts` is homed in `src/panels/` but is an app-wide seam.** 19 downstream dependents across app, studios, panels, and the parked studio; `vite.config.ts` must name it individually to keep it in the initial-shared graph. Move it to the interaction home (or the post-T2 studio-shell home) and the special case disappears.

**G5 — `src/state/projectDurability.ts` at 686 LOC.** Fourteen lines under the hard ceiling; it must be split before any feature lands in it.

## Fine

**Store architecture (question 2) — healthy, leave the shape alone.** The split is coherent and layered, not a catch-all: action recipes per family (`src/state/actions/`) → `createAuthoredDispatcher` (gesture preview, durability reservation, journal handoff) → `reduceAuthoredOperationState` (validation-first: target equality, pose-revision freshness, unique identities, inverse derivation before accept) → narrow session repair. `createHistoryCoordinator` is a genuine single owner for batches and transient gesture previews, with previews explicitly outside Zustand until commit. `CubicellState` documents session-only versus persisted fields inline. Aside from T4's seam naming, I found nothing here that restructuring would improve.

**Studio boundaries (question 3) — a real boundary, not a naming accident, and it scales.** The concept has a contract (`src/studios/contract.ts`), generation-safe lifecycle (`studioContext.ts`, disposal in reverse order, stale-generation guards), a catalog with per-studio lazy loaders, per-studio delivery roots in the budget, and a `CROSS_STUDIO_IMPORT` gate in `scripts/check-delivery-budget.mjs`. Adding a studio costs a `catalogData` entry, a loader, and a budget delivery block; `DesignSystemStudio.tsx` at 8 LOC shows the floor. The threats to it are T2 (the "app" grab-bag a new studio would raid) and G1 (the `src/studio/` name collision), both incremental.

**Panels and the motion timeline (question 4) — well separated in both directions.** `usePieceMotionModel` is a single documented derivation feeding dock filmstrip and right-rail inspector, so they cannot disagree; panel-local view state lives in `motionFocusContext`, durable layout in `userProjectState.panelLayout`, and the model reads the document only through `selectAuthoredWorkbench`. Domain operations issued from panels go through the command vocabulary or documented direct store actions; `src/panels/stateCapture.ts` builds operations, it does not apply them. No leakage found in either direction.

**Delivery budgets (question 5) — shaping healthily overall.** `trackedDebt` is empty (all prior slices completed their removals), `anchoredByDesign` entries carry reasons and are validated as cut vertices rather than global exemptions, and the checker validates its own config. The one recurring cost is T3's ownership map.

**Composition-layer testability (question 6) — structurally sound.** See Walls. The real risk is cultural (harness proliferation), and the countermeasure is a rule about which root integrator tests must mount, which is cheap because the root is already mountable.

**File and module health (question 7).** All files under the 700 ceiling; duplication effectively zero; `src/controls/`, `src/thumbnail/`, `src/config/cubicellConfig.ts` (feel knobs centralized, consistent with project preference), `src/editor/` keyboard/commands/affordances split, and the `FeatureSlot`/`LazyCapability` machinery (transactional prepare/commit, generation-safe, preview overrides) are all cohesive and correctly sized.
